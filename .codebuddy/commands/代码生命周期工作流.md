### 【系统配置】

**角色**：代码生命周期工序编排器（Workflow Router）。
**核心初衷**：把分散的工序命令（任务书 / 地基前瞻 / 写码 / 测试门禁 / 架构 / 系统治理 / 排查 / 债务 / ADR / 删 / 记一下）串成一条自包含的流水线，让 AI 在任何起点都能判断"此刻该调哪份命令"，避免漏工序、重复写、或地基没铺就盖楼。
**定位边界**：本文件只做**路由与顺序编排**，不替代任何一份命令的具体动作。每份命令内部自包含，本文件不重复其规则、不引用外部文档。
**绝对禁令**：

禁止跳地基：进入写码前，若涉及新功能或存量改造且全局基建未打好过，必须先打地基（地基前瞻5步法）。地基缺失时写码 = 边盖楼边通水电网。

禁止跳过门禁：写码完成后须经测试门禁（按改动级别）判绿，才视为可交付；红灯须退回写码改，不得带红放行。

禁止重复造工序：各份命令职责互不重叠，同一任务同一时刻只激活一份，不并行混淆。

禁止绕过两道闸：改**新页面 UI** 前必须有 `USER APPROVED PAGE: /route`；新增**控件**必须有"同意新增 <控件名>"。没有这两句口令，页面契约与控件准入都不算通过。

### ## 工序总览

```
[PRD5步法] ─定做什么─▶ [地基前瞻5步法] ─地基打好─▶ [写代码4步法] ─落地实现─▶ [测试门禁5步法] ─判绿─▶ [架构5步法]
  任务书三段式            项目级地基门禁              功能级实现              分级回归收口            存量翻新/深化
```

旁路与留痕命令（可随时介入，但不改变主链顺序）：

- **PRD5步法**：从模糊需求收敛出模块 + 约束 + 验证标准，产出**任务书三段式**（`docs/plan/`，人对着模板核；格式闸已删）。空白起点必跑。
- **地基前瞻5步法**：项目初始 / 刚写一部分时，前瞻定好并落地依赖 / 全局配置 / 共享基建 / 全局契约 / 环境可跑。
- **写代码4步法**：定契约（含收口检索防功能重复）→ 定数据流（唯一入口）→ 构思测试 = 细化契约 → 施工。
- **测试门禁5步法**：写码后按改动级别（L0~L3）跑对应测试，红灯退回写码。
- **架构5步法**：存量代码出现浅模块（职责碎、接口宽）时深化重组；也可在写码后回头收拾。
- **系统治理5步法**：周期 / 主动触发的"体检 + 打扫"旁路（残留 / 依赖 / 文档 / 契约漂移 / 架构熵 / 债登记），只扫列清单不擅自动。
- **排查5步法** + **运行时debug法**：出 bug 时的"怎么想"与"证据从哪来"两件套。
- **债务登记5步法**：发现"现在不能动、但确是债"的项 ⇒ 登记进 `daily/架构日志/债务.md`（`node scripts/debt.mjs`）。
- **ADR守护者**：确立 / 推翻判据 ⇒ `docs/adr/`（`node scripts/adr.mjs add`）。
- **删.md**：清障式删除（删 = 副产品，不是独立目标）。
- **记一下**：把本次做了什么 / 踩了什么坑 / 欠了什么债 落到唯一真源。

### ## 路由判定（从当前状态选入口）

| 当前情景 | 激活命令 | 完成后流向 |
|---|---|---|
| 从零新功能 / 需求模糊 | PRD5步法（产出任务书） | → 地基前瞻5步法 |
| 任务书已定，准备动手写 | 地基前瞻5步法 | → 写代码4步法 |
| 地基已打好，开始实现某功能 | 写代码4步法 | → 测试门禁5步法 |
| 写码完成，准备交付 / 验证 | 测试门禁5步法 | 绿灯→可交付；涉及存量翻新→架构5步法 |
| 写了/接手了存量代码，发现浅模块、难维护 | 架构5步法 | → 翻新后回到写代码4步法补功能 |
| 改造涉及全局基建（依赖 / 配置 / 共享件 / 全局契约） | 地基前瞻5步法（优先） | → 写代码4步法 |
| 改新页面 UI / 新增控件 | 页面契约 + 控件准入两道闸（`docs/CONVENTIONS.md` 的页面契约 / 控件准入两节） | 通过口令后 → 写代码4步法 |
| 用户说"清理/优化/瘦身/体检/性能/技术债" | 系统治理5步法（旁路，纯主动触发） | — |
| 发现"现在不能动、但确是债" | 债务登记5步法 | — |
| 要确立 / 推翻一条约定 | ADR守护者 | — |
| 运行出错 / 不知哪坏 / debug | 运行时debug法（证据采集层）+ 排查5步法（推理层）；前者补后者的证据，组合使用 | — |

### ## 分流铁律

1. **新需求走前四段**（PRD → 地基 → 写码 → 测试门禁），顺序不可颠倒；地基缺失不许写码，写码完必经门禁。
2. **架构5步法是旁路**，不在正常新功能主线上，仅在"存量代码要收拾"时介入，介入后可回流写码补功能。
3. **写码4步法的 State 1 收口检索**是防"写两遍"的主闸门：动手前必检索既有同类实现（`grep -rln "<概念词>" src`），复用优先；命中 > 1 处 ⇒ 先合并，不许新建。
4. **地基前瞻的 State 3/4** 是防"全局基建写两遍"的闸门：共享件与全局契约先钉死唯一入口、前瞻落地。
5. **测试门禁按级不越级**：L0 只静态闸，L3 才全量 `npm test` + `npm run build`；红灯必退回写码改绿，禁止带红交付。
6. **两道闸不可绕过**：新页面 UI 与新控件各自有批准口令；"好 / 继续 / 可以"都不算。
7. 任何命令产出的清单 / 任务书 / 架构记录，按各命令自身约定存档（任务书 → `daily/架构日志/` 或 `docs/plan/`；地基蓝图 → `daily/架构日志/<NN>-<区域>-<日期>.md`；治理清单 → `daily/架构日志/`；日志 → `docs/CHANGELOG.md`），本文件不另设存档格式。
