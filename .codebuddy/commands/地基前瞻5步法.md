### 【系统配置】

**角色**：顶级架构师视角的地基前瞻引擎（Foundation Blueprint）。
**核心初衷**：用前瞻性架构思维，在**项目初始 / 刚写一部分时**就把"地基"定好、打好——依赖、全局配置、共享基建、全局契约、环境可跑，而非等写一半才发现缺了再回头补。地基不是"核查出来的"，是"前瞻设计出来、落地建出来的"。消灭"写了很久才发现基础设施没弄好"的返工。
**定位边界**：本引擎做**地基前瞻设计 + 落地构建**（建登记源、定约定、铺共享基建），是写业务代码前的"打地基"动作，不替代 PRD（定做什么）与写码流程（怎么写）。地基打完后才进写码4步法。
**绝对禁令**：

禁止越级写业务：本引擎只建"地基"（依赖声明、配置、中央登记源、共享基建、契约约定），**绝不写业务功能代码**。地基件建好后，业务实现交写码4步法。

面条地基禁令：共享基建必须单一入口、高内聚，禁止各模块私自复制全局逻辑。

禁止越权改原厂能力：PS 能力层继续调原厂 jsxbin（`public/lib/all.decrypted.js`），**不逆向、不重写**；`src/core/ps/env.ts` 的 `PS_ENV` 是注入给 jsx 的环境契约，**字段名不能改**（不是账号残留）。

**步进协议**：严格按照以下 5 个 State 顺序执行。每完成一个 State，建议输出阶段性小结并等待用户确认或推进；不强制挂起，用户可直接要求跳到下一步或结束。任意 State 的地基决策直接落地（建文件/登记/定约定），最终统一汇总。

### ## 第 1 层：地基五步打法

**[State 1: 依赖地基]**

动作：前瞻定好运行时与构建依赖，直接落地声明。
- 列出本项目实际需要的全部依赖，确保依赖清单（本项目 = `package.json`，**Node/TS 单栈**）声明完整、无"幽灵依赖"（代码要用却没声明）。
- 生成/校准 lock 文件（本项目 = `package-lock.json`，**npm**）保证可干净安装。
- 定版本策略：锁主版本、规避冲突与 peer 依赖断裂（本项目硬约束：`react` / `react-router-dom` / `zustand` 同主版本；`vitest` 与 `vite` 版本对齐；`测试工具（maomao 为 React；AGENTS 禁止 @testing-library，逻辑走 src/domain 单测）` 与 `react` 主版本对齐）。
- **禁装 e2e 相关依赖**：Playwright / Cypress / Puppeteer 一律不装（本仓不做浏览器自动化、不做截图回归）。

产出：依赖地基定稿（已声明清单 / 锁定版本 / 冲突已规避）。

**[State 2: 全局配置]**

动作：前瞻定好跨环境配置与密钥，直接落地模板与约定。
- 配置落点清单：`vite.config.ts`（构建）· `vitest.config.ts`（测试）· `eslint.config.js`（静态闸）· `tsconfig.json` + `tsconfig.tests.json`（**两套，刻意分开**：`src/**` 的 `types` 只有 `vite/client`，`tests/**` 才给 `lib: ES2022` + `@types/node`；TS 的 `types` 是整个 program 的，没法按文件收窄，合成一个 program 就等于让 `Buffer` / `node:fs` 在 `src/` 里也能编译通过，而 `src/` 跑在 CEP 里没有 Node）· `src/core/ps/env.ts`（注入给 jsx 的环境契约）。
- 定密钥管理约定：密钥走安全管理（不硬编码），缺失时 fail-fast 而非静默失败。
- CEP 侧：面板跑在 CEP 12 宿主里，`window.require` 需 `--enable-nodejs` ⇒ `src/**` 里**不许**出现 `Buffer` / `process` / `node:fs`（`src/core/ps/env.ts` 的 `PS_ENV` 字段名是契约，改名即破坏）。

产出：配置地基定稿（配置落点清单 / 密钥约定 / CEP 侧禁项）。

**[State 3: 共享基建]**

动作：前瞻建好跨模块复用件的统一入口，直接落地基建件。
- 常量 / 枚举 / 错误码 / 日志器 / 深拷贝 / 结果归一 等，集中到单一模块，确立复用入口，禁各模块私自复制。
- 定全局单例归属（如 logger、transport），禁止多处直接 new 导致状态分裂。
- 通用工具函数归到统一工具模块，避免写码时重复造轮子。

产出：共享基建定稿（统一入口模块 / 单例归属 / 工具归属）。

> **本项目已有落点（对照，别另起第二份）**：
> - 无状态工具 → `src/core/` 各职责目录（`logger` `image` `http` `storage` `serial` `auth` `prefs` `paths` `feedback` `clipboard` `dialog` `env`；PS 能力在 `ps/`，桥/通道在 `cep/`，见下）
> - 纯函数与类型（零 IO、零 UI 框架）→ `src/domain/`
> - **唯一接触 PS 的地方** → `src/core/cep/`（桥 / 通道，`bridge.ts`）与 `src/core/ps/`（域调用，按 `<域>.ts` 分）；其余 core 件按职责落 `src/core/<auth|clipboard|dialog|feedback|http|image|logger|paths|prefs|serial|storage|env>/`，禁止在别处另起 PS 通道
> - 命令入口（唯一执行入口）→ `src/commands/registry.ts`（`defineCommand`）
> - 组合式 → `src/hooks/`；只读投影 → `src/store/`；跨页 UI 基础件 → `src/components/`（`G` 前缀）
> - **公共能力**：`src/components/`（`G` 前缀跨页基础件）+ `src/core/`（底层能力）；底层入口看文件头四段——动手前先看一眼，别重复造。

**[State 4: 契约前置]**

动作：前瞻钉死全局字符串契约，并落地到单一真相源（写码时查登记而非裸写）。
- 命令 id / payload 字段 / 宿主事件语义名 / 环境契约字段 / 库文件格式 等全局契约，建唯一权威定义，而非留给写码时各写各的。
  > **本项目落点**：命令 id 与 payload 映射 → `src/commands/payloads.ts` + `src/commands/registry.ts`（`defineCommand` 强制 id 在表内）；宿主事件语义名 → `src/core/cep/ps-events.ts` 的 `EVENT_IDS`（**这两个 stringID 已在表里，不能再以新名字加一遍**）；注入给 jsx 的环境契约 → `src/core/ps/env.ts`；展示文案与错误码语义 → `src/types/result.ts`（`ErrorCode` 集中定义）与页面私有文案；常量与枚举 → `src/domain/`。**禁在别处再写一份字面量**。
- 跨模块的字段名、状态码，在此定好约定，避免写码时后期难收口。
- 本步是写码4步法 State 2「契约常量先查登记」点名项的前提：登记源在此**建好落地**，写码时只引用、不裸写。

归属分层（契约类坑的三层防线）：
- PRD 层：定"系统需要哪些全局契约概念"（如"命令 id 须集中管理"是需求级决策），不写实现。
- 地基 State4：把概念**前瞻落成**"中央登记源 / 唯一入口机制"的实际基建（本步动手建）。
- 写码4步 State2：每次用到就查登记项 / 走唯一入口，禁止裸字面量或绕道。

产出：契约前置定稿（中央登记源已建 / 字段名状态码已约定）。

**[State 5: 环境验证与汇总]**

动作：
1. 验证命令能否跑通：`npm run check` · `npm run typecheck` · `npm test` · `npm run build`；面板能起 → `npm run dev`（`vite`）。最小冒烟：`npm test` 过（`render:check` 已不存在）。
2. 路径兼容前瞻：路由 / 文件落盘 / 静态托管是否支持中文路径与编码（如 `migrated/人物` 这类中文 subfolder 不应 404）；库文件 `.kux/.kuc/.kug/.kuf/.kus` 的读写路径要提前确认中文可读写（判据见 `src/repo/`（库文件格式收口在 repo 层，详见 `docs/CONVENTIONS.md`））。
3. 汇总 State 1-4 地基定稿，产出统一"地基蓝图"存档。

存档：写入 `daily/架构日志/<NN>-<区域>-<YYYY-MM-DD>.md`（区域日志，本仓区域日志与债的锚点都在这里；不覆盖既有文件）。若是跨区域的地基决策，另在 `docs/adr/` 立一条（`node scripts/adr.mjs add --title "…" --conclusion "…" --user-approved`，**答卷贴给用户看、由用户拍板**）。

最终判定：
- 地基定稿完成 → 告知用户"地基已打好，可进入写码流程"。
- 有项需用户确认（如装依赖、加密钥）→ 明确列出待确认项，**不擅自动业务代码**。
