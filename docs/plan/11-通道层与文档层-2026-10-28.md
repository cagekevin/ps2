# 深模块计划 A：PS 通道层 · 能力表（2026-10-28）

> 目标：**以后每加一个 PS 能力，不再重写一遍「前置检查 → 调用 → 解析 → 翻译错误」**。
> 只做一件事：把 26 个能力函数里重复的 3–5 步流程，收成「一张表 + 一个执行器」。

## A.1 现状（全部有出处，不凭印象）

### 一次能力调用现在的实际步骤

以 `core/ps/font.ts:140` `setFontByNames` 为例，一个能力要自己走完：

| 步 | 代码 | 出处 |
|---|---|---|
| 1 前置 | `requireVendor()` | `font.ts:145` |
| 2 前置 | `requireTextLayer()` | `font.ts:149`（今天刚加） |
| 3 调用 | `callJsx('ztgl_setFont', [...], { timeout: WRITE_TIMEOUT })` | `font.ts:152` |
| 4 约定值 | `unwrapRaw(call.value)` | `font.ts:157` |
| 5 解析 | `parseJsxRaw(call.value)` | `font.ts:160` |
| 6 取 err | `errOf(parsed.value, call.value)` | `font.ts:163` |
| 7 翻译 | `err === 1` → `envelopeMessage(...) \|\| FONT_UNAVAILABLE` | `font.ts:165-171` |

## A.2 目标接口（2026-10-28 定稿）

新增两个文件，**不改任何现有能力的对外签名**。与初版的三处差异见本节末尾。

```ts
// src/core/ps/capability.ts —— 唯一执行器
export type Channel = 'direct' | 'dispatch';
export type Gate = 'core' | 'vendor';

export interface CapabilitySpec<T> {
  readonly fn: string;                            // jsx 函数名（与 jsx 侧同名镜像）
  readonly gate: Gate;                            // 缺能力先报 PS_UNREADY，不报图层不对
  readonly channel: Channel;                      // direct = 直调 fn(...)；dispatch = ps_onJsx({f,arr,n})
  readonly timeout: number;                       // 必填，见 A.3.5 ①
  readonly parse: Parser<T>;                      // 返回什么形状 + 多严格，都由它决定
  readonly require?: () => Promise<Result<void>>; // 前置，直接引用 layer.ts 的函数
  readonly silent?: boolean;                      // 轮询类不记日志
  readonly label?: string;                        // dispatch 通道的 n 标签
}

export function callCapability<T>(spec: CapabilitySpec<T>, args?: unknown[]): Promise<Result<T>>;
```

```ts
// src/core/ps/capabilities.ts —— 表。一行一个能力，是「唯一事实」
export const CAP = {
  setFont: {
    fn: 'ztgl_setFont', gate: 'vendor', channel: 'direct',
    timeout: WRITE_TIMEOUT, require: requireTextLayer,
    parse: strictVoid(FONT_UNAVAILABLE)
  },
  textInfo: {
    fn: 'zt_getFontSimpleInfo', gate: 'vendor', channel: 'direct',
    timeout: READ_TIMEOUT, require: requireTextLayer,
    parse: strictData('当前图层没有可读的文字属性')
  }
  // … 逐批搬进来
} satisfies Record<string, CapabilitySpec<unknown>>;
```

`callCapability` 内部固定四步，与今天逐字等价：

| 步 | 动作 | 现状出处 |
|---|---|---|
| 1 gate | `spec.gate` → `requireVendor()` / `requireCore()`，失败 `PS_UNREADY` | `vendor.ts:35`、`layer.ts:29` |
| 2 require | `spec.require()` 失败原样透传（`PS_WRONG_LAYER` 等） | `font.ts:149`、`text.ts:40` |
| 3 call | `callJsx(fn, args, { timeout, silent })`；dispatch 先包 `{ f, arr, n }` | `vendor.ts:37-40` |
| 4 parse | `spec.parse(raw)` | 见下表 |

### 解析器（`raw.ts`，六个具名实现，不再有 `shape` 枚举）

| 解析器 | 现状出处 | 顺序 | 解析不出 JSON 时 |
|---|---|---|---|
| `passthrough` | `font.ts:129` | 原样返回 raw | 不管（调用方判 `isOkSentinel`） |
| `unwrapRaw` | `vendor.ts:43-44`、`style.ts:40-41` | 只折约定值 | 不解析 JSON |
| `lenientVoid(fb)` | `vendor.ts:59-85`（`runDirect`） | `unwrapRaw → parseJsxRaw → err===1` | **当成功** |
| `strictVoid(fb)` | `font.ts:140-173`、`font.ts:92-115` | `unwrapRaw → parseJsxRaw → errOf → err===1` | `CORRUPT` |
| `strictData(fb)` | `text.ts:37-58` | `parseJsxRaw → err 是数字且 ≠0 → dataOf` | `CORRUPT` |
| `parseDataEnvelope` | `text.ts:61-82`、`:124-130` | 拆 `data`，不判 err、不折约定值 | `CORRUPT` |

`strictData` 与 `parseDataEnvelope` 都**不折约定值**：`no-doc` 会落成 `CORRUPT`，而 `-1` 是合法 JSON 数字、会原样交出去（已由单测钉住）。这是既有行为，`StateHint` 的灰字与红字就靠这个码区分，迁移时不许"顺手"补 `unwrapRaw`。

### 三处定案（与初版的差异）

1. **`shape` 枚举 → `parse` 函数**：`shape` 与 `strict` 是两个正交维度，能写出 `{ shape: 'raw', strict: true }` 这种无意义组合（违反 `CONVENTIONS` §0.5 原则二「类型闭合」），执行器里必然长出 switch。改成存解析函数后，非法组合在类型上不存在，加第 7 种形态只改 `raw.ts`，执行器不动。
2. **`gate` 进表**：`mm_*` 走 `requireCore`（`style.ts:34`、`layer.ts:29`、`diag.ts:29`），`ys_ / zt_ / cy_*` 走 `requireVendor`。没有 `gate`，M4 的 `mm_style_*` 与 `layer.ts` 进不了表。
3. **`fallback` 并进解析器**：写成 `strictVoid(FONT_UNAVAILABLE)`，不在 spec 上单列 `fallback`，否则会出现「有 fallback 但解析器是 passthrough」的空转。`FONT_UNAVAILABLE` 由 `capabilities.ts` 导出，`font.ts` 的 `applyFont` 共用一份。

### 唯一不等价点

门失败时 `detail` 统一成 `vendor:false` / `core:false`。今天 `style.ts:34` 给 `''`、`layer.ts:29` 给 `'core:false'`。`code` 与 `reason` 不变，只影响 `detail`（进日志与 `StateHint` 的 title）。

### 不搬进表的能力（2026-10-28 修订）

初版列了 4 个，实际只留 2 个：

| 函数 | 留的理由 |
|---|---|
| `font.checkFontUsable` | `err===1` 要带宿主 `msg`，且**不折失败**（信封不成立按可用处理），与任何解析器都不同 |
| `style.saveLayerStyle` | `err===1` 折 `PS_ERROR` 而非 `VALIDATION`，且没有 `false` 分支，与 `strictVoid` / `strictPayload` 都不同档 |

~~`getFontInfo`~~ 与 ~~`getGradientInfo`~~ **已进表**：两者是同一个骨架（`false` → `VALIDATION`、`{err:1}` → `PS_ERROR`、载荷校验 → `ok`），只差文案与载荷判定。初版判「形态各自唯一」是错的——同一骨架两个函数就是两处实现。现在共用 `raw.strictPayload({ whenFalse, whenFailed, accept })`。

## A.3.5 复核：四处会让计划翻车的地方（二次核对，逐条有出处）

### ① 超时不能按 shape 推，必须逐条写

实测各调用点的超时**互不相同**：

| 调用点 | 超时 |
|---|---|
| `text.ts:43/67/79`（读） | 默认 30s |
| `font.ts:39/57`（ys_* 读） | 默认 30s |
| `font.ts:99`（ys_useFont） | 60s |
| `font.ts:129`（系统字体列表） | **300s** |
| `font.ts:152`（ztgl_setFont） | 60s |
| `text.ts:127`（zt_setFontColor） | 60s（显式） |
| `runDirect` 全部（23 个写） | 60s |
| `runVendor` 全部（调度） | **30s**（默认，不是 60s） |

→ 表里 `timeout` **必填**，不许有"按通道取默认"。否则 `dispatch` 从 30s 变 60s、`ztgl_initSystemList` 从 300s 掉到 30s（扫全机字体会被判超时）。

### ② `shape` 三种不够，实际有四种解析形态

| 形态 | 现实现 | 例子 |
|---|---|---|
| `void` | `runDirect` / `runVendor` | 23 个写 + 调度 |
| `raw` | 直接返回原始串 | `ztgl_initSystemList`（哨兵 `ok`） |
| `err` | `unwrapRaw` → `parseJsxRaw`（**失败=CORRUPT**）→ `errOf` → `err===1` | `setFontByNames`（`font.ts:157-171`） |
| `lenient-err` | `unwrapRaw` → `parseJsxRaw`（**失败=成功**）→ `err===1` | `runDirect`（`vendor.ts:73`） |
| `data` | `parseJsxRaw` → **`err !== 0` 即失败** → `dataOf` | `getTextInfoRaw`（`text.ts:46-57`） |
| `data-loose` | `parseDataEnvelope`（**不判 err**、**不判约定值**） | `getCurrentFontInfoRaw`（`text.ts:69`） |

→ ~~`shape` 定义为 6 种~~ **已被 §A.2 定稿取代**：不再有 `shape` 枚举，改成 `raw.ts` 的具名解析器（`passthrough` / `unwrapRaw` / `lenientVoid` / `strictVoid` / `strictData` / `parseDataEnvelope` / `sentinelJson`）。下面这行清点的是**当时实际存在的形态**，形态结论仍然成立。
注意 `data-loose` 在收到 `no-doc` 时会报 `CORRUPT`（因为没走 `unwrapRaw`）——**这是既有行为**，迁移时必须保留，否则错误码变化会让 UI 从灰字变红字。

### ③ 「加前置」是行为变更，必须单独一步

`text.ts` 的 23 个写函数走 `runDirect`，而 `runDirect` 里**没有** `requireTextLayer`（`vendor.ts:59-66`）。
如果 M3 顺手把 `require: 'text'` 加到表里，这 23 个能力的失败码会从 `VALIDATION`（宿主 msg）变成 `PS_WRONG_LAYER`。

两者对用户都是「当前图层不是文字图层」，但：
- 码变了 → `StateHint` 的语气分支变了（灰字规则按码判）；
- 真机验证面从 3 个场景变成 23 个能力 × 2 场景。

→ 拆成 **M3（只搬解析，前置原样保留）+ M3b（逐个加前置，每个能力单独验证）**。M3 结束时行为必须逐字节等价。

### M3b 改为「按证据加一行」，不批量加（2026-10-28 定）

`M3` 完成后重新对账，发现批量加前置与计划假设相反：

| 事实 | 出处 |
|---|---|
| 写函数在非文字图层上**自己给一句人话** | 真机日志 `{"err":1,"msg":"请选择文字图层","code":0}`（`ztgl_setFont` / `zt_setFontName`） |
| `lenientVoid` 已经把这句原话交给用户 | `raw.ts` 的 `envelopeMessage` 优先，兜底才用表里的文案 |
| 加前置才必要的，是**直接抛异常**的那批 | 3 个读 + `ys_useFont` + `ztgl_setFont`，抛「命令"获取/设置"当前不可用」 |

所以 22 个写批量加 `require` 的实际交易是：**用每次多一次 `mm_layer_getState` 往返，换提示码从 `VALIDATION` 变 `PS_WRONG_LAYER`（灰字、不算故障）**。而 22 个里哪几个是「抛异常」而不是「返回 err+msg」，目前没有数据。

判定规则（真机时执行）：

- 某个写在非文字图层上**抛**「命令"设置"当前不可用」→ 给它那一行加 `require: requireTextLayer`，码变 `PS_WRONG_LAYER`；
- 已经返回 `{err:1, msg:"请选择文字图层"}` → **不加**，保留宿主原话，不多一次往返；
- 加过之后要复验一次：正常文字图层上的行为必须不变（多出来的那次 `mm_layer_getState` 只看 `kind`，不写任何东西）。

#### 2026-10-28 真机再改判（推翻上面这段）

上面的判定规则建立在「写函数会自己给人话」上。真机日志推翻了一半：

```
zt_setTextAlignment    args:[0]        raw:"undefined"
zt_setBackrgoudAlign   args:[3]/[4]    raw:"undefined"
zt_createButton        args:[{...}]    raw:"undefined"
```

这三条都是在**智能对象**上点的（同一时段的日志确认图层类型）。它们**既不给 `{err:1}`、也不抛「命令不可用」，而是返回 `undefined`、什么都不做**——`lenientVoid` 当成功 → 界面提示成功、图层没变。

而且返回值**区分不了成功与空转**：文字图层上大概率也是 `undefined`。所以「看返回什么再决定」这条路根本不通。

结论：**文字属性类能力（22 个写 + 4 个读 + 字体应用 2 个）一律声明 `require: requireTextLayer`**，由执行器第一步判定、不通过直接终止。判定成本是每次调用多一次 `mm_layer_getState`（与操作本身同一量级，可接受）。

不采用「UI 按图层置灰」的理由：判定会变成两处（UI 用 800ms 前的 store 值、能力层用现查值），且准确性更差。前提是「这一步能不能做」，属于调用入口的事，写在表里只有一处。

## B.2 目标接口（已落地，2026-10-28）

```ts
// repo/json-file.ts
export interface Dropped { path: string; code: ErrorCode; reason: string }
export type DropPolicy = 'reject' | 'filter';

/** 列表解码：逐项解码，按策略决定「一项坏 = 整份失败」还是「丢掉那一项」 */
export function decodeList<T>(
  raw: unknown,
  item: (value: unknown, path: string) => Result<T>,
  policy: DropPolicy
): Result<{ items: T[]; dropped: Dropped[] }>;
```

两处与初版不同：

1. `Dropped` 多一个 `code`。只有 `reason` 的话，机器侧分不清「字段缺失」与「类型不对」，而这正是排障要的。
2. **不要 `onDropped` 回调**。`decodeList` 的返回值里就带着 `dropped`，repo 把它包进自己的返回值交给 store 即可；多一个回调等于多一条「谁记得调它」的隐式契约。

- 反向：把文件顶层改成 `{}`（不是数组）→ 仍应整份 `CORRUPT`（结构性错误不能过滤）。

## B.5 风险

### ① `filter` 会静默丢数据

丢掉的那一项如果用户看不出来，就是新的「说谎」。→ `dropped` 必须一路冒到 UI（`StateHint` 显示「N 项无法识别，已跳过」），且**写回时先提示用户**，不能"读的时候跳过、写的时候删掉"。

### ② 写回会洗掉未知键（最危险的一条）

现在写路径用 `RawRecords`（`json-file.ts:198`，`Record<string, unknown>[]`）**原样保留未知字段**，注释写明「丢掉就会改坏用户数据」。

如果 `decodeList` 返回的是解码后的 `T[]`，再整份写回，用户文件里的未知字段就没了——**这是静默的数据损坏**，且不可逆（`.bak` 只有上一版）。

→ 约束：`decodeList` 必须同时返回 `items: T[]` **和** `records: RawRecords`（原始对象引用），写回一律用 `records`，只在"用户显式新增/删除"时才重建。B-M1 的单测必须包含这条：**未知键写入后仍在**。

### ③ 与 A 的先后

B 不依赖 A，但两者都动 `repo`/`core`，同时改会让真机定位困难。→ 先 A-M1（2 个能力），真机确认后开 B-M1，A 的 M3 与 B 的 M2 不要同一天做。
