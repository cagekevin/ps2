## A.2 目标接口

新增两个文件，**不改任何现有能力的对外签名**：

```ts
// src/core/ps/capability.ts —— 唯一执行器
export type Channel = 'direct' | 'dispatch';
export type Shape = 'void' | 'raw' | 'json' | 'data' | 'err';

export interface CapabilitySpec {
  fn: string;                 // jsx 函数名（与 jsx 侧同名镜像）
  channel: Channel;           // direct = 直调 fn(...)；dispatch = ps_onJsx({f,arr,n})
  shape: Shape;               // 返回什么形状，决定用哪个解析器
  timeout?: number;           // 缺省：direct 读 30s / 写 60s，dispatch 60s
  strict?: boolean;           // 解析不出时：true=CORRUPT，false=按成功（保留 UNVERIFIED 行为）
  require?: LayerKind[] | 'text' | 'shape';  // 前置：图层类型（走 layer.requireLayerKind）
  fallback?: string;          // err:1 且宿主没给 msg 时的兜底文案
  silent?: boolean;           // 轮询类不记日志
  label?: string;             // dispatch 通道的 n 标签
}

export async function callCapability(spec: CapabilitySpec, args?: unknown[]): Promise<Result<string>>;
```

```ts
// src/core/ps/capabilities.ts —— 表。一行一个能力，是「唯一事实」
export const CAP = {
  setFont:        { fn: 'ztgl_setFont', channel: 'direct', shape: 'err',  require: 'text', fallback: '字体不可用（系统里可能没装这个字体）' },
  fontSimpleInfo: { fn: 'zt_getFontSimpleInfo', channel: 'direct', shape: 'data', require: 'text', strict: true },
  systemFontList: { fn: 'ztgl_initSystemList', channel: 'direct', shape: 'raw', timeout: LONG_TIMEOUT },
  // … 逐批搬进来
} as const satisfies Record<string, CapabilitySpec>;
```

`callCapability` 内部固定七步，与今天逐字等价：

1. `channel === 'dispatch'` → `requireVendor()`
2. `spec.require` → `requireLayerKind(...)`（`core/ps/layer.ts:65`）
3. `callJsx(spec.fn, args, { timeout, silent })`；dispatch 通道先包 `{ f, arr, n }`
4. `unwrapRaw(raw)` —— 约定值表 `raw.ts:16`
5. `spec.shape === 'raw'` → 直接返回 raw（哨兵 `isOkSentinel` 由调用方判）
6. `strict === false` → 解析失败按成功返回 raw；否则 `parseJsxRaw` 的错误原样返回
7. `shape === 'err'` → `errOf` + `err === 1` → `envelopeMessage || spec.fallback`；`shape === 'data'` → `dataOf`

## A.3.5 复核：四处会让计划翻车的地方（二次核对，逐条有出处）

### ① 超时不能按 shape 推，必须逐条写

实测各调用点的超时**互不相同**：

| 调用点 | 超时 |
|---|---|
| `text.ts:43/67/79`（读） | 默认 30s |
| `font.ts:39/57`（ys_* 读） | 默认 30s |
| `font.ts:99`（ys_useFont） | 60s |
| `font.ts:129`（系统字体列表） | **300s** |
| `font.ts:152`（ztgl_setFont） | 60s |
| `text.ts:127`（zt_setFontColor） | 60s（显式） |
| `runDirect` 全部（23 个写） | 60s |
| `runVendor` 全部（调度） | **30s**（默认，不是 60s） |

→ 表里 `timeout` **必填**，不许有"按通道取默认"。否则 `dispatch` 从 30s 变 60s、`ztgl_initSystemList` 从 300s 掉到 30s（扫全机字体会被判超时）。

### ② `shape` 三种不够，实际有四种解析形态

| 形态 | 现实现 | 例子 |
|---|---|---|
| `void` | `runDirect` / `runVendor` | 23 个写 + 调度 |
| `raw` | 直接返回原始串 | `ztgl_initSystemList`（哨兵 `ok`） |
| `err` | `unwrapRaw` → `parseJsxRaw`（**失败=CORRUPT**）→ `errOf` → `err===1` | `setFontByNames`（`font.ts:157-171`） |
| `lenient-err` | `unwrapRaw` → `parseJsxRaw`（**失败=成功**）→ `err===1` | `runDirect`（`vendor.ts:73`） |
| `data` | `parseJsxRaw` → **`err !== 0` 即失败** → `dataOf` | `getTextInfoRaw`（`text.ts:46-57`） |
| `data-loose` | `parseDataEnvelope`（**不判 err**、**不判约定值**） | `getCurrentFontInfoRaw`（`text.ts:69`） |

→ `shape` 定义为 6 种：`void | raw | err | lenient-err | data | data-loose`。
注意 `data-loose` 在收到 `no-doc` 时会报 `CORRUPT`（因为没走 `unwrapRaw`）——**这是既有行为**，迁移时必须保留，否则错误码变化会让 UI 从灰字变红字。

### ③ 「加前置」是行为变更，必须单独一步

`text.ts` 的 23 个写函数走 `runDirect`，而 `runDirect` 里**没有** `requireTextLayer`（`vendor.ts:59-66`）。
如果 M3 顺手把 `require: 'text'` 加到表里，这 23 个能力的失败码会从 `VALIDATION`（宿主 msg）变成 `PS_WRONG_LAYER`。

两者对用户都是「当前图层不是文字图层」，但：
- 码变了 → `StateHint` 的语气分支变了（灰字规则按码判）；
- 真机验证面从 3 个场景变成 23 个能力 × 2 场景。

→ 拆成 **M3（只搬解析，前置原样保留）+ M3b（逐个加前置，每个能力单独验证）**。M3 结束时行为必须逐字节等价。

### ④ 回滚粒度

| 阶段 | 回滚动作 | 代价 |
|---|---|---|
| M1（3 个试点） | 3 个函数体改回 | 5 分钟，无连带 |
| M2（前置进表） | 表里删 `require` + 函数体加回 | 5 分钟 |
| M3（23 个写） | 单文件 `git checkout text.ts` | 10 分钟，但要重跑该文件的单测 |
| M4（style / common-use） | 同上，按文件 | 这两处解析最杂（`style.ts:139` 跨行调用、`common-use.ts:123/131` 无解析），风险最高，放最后 |

**结论**：M1 缩到 **2 个能力**（`ztgl_setFont` + `zt_getFontSimpleInfo`），把 `data` 与 `err` 两种形态各验一遍；`ztgl_initSystemList` 的 300s 与哨兵放到 M1b 单独验。这样第一轮 diff 最小、真机只需 2 个场景。

## A.5 不做 / 风险

- **不顺手收紧 `strict`**：`runDirect` 的宽松解析是 UNVERIFIED 的历史妥协，收紧会把今天正常的操作判成失败。收紧要单独一轮 + 真机证据。
- **不动 jsx 侧**：`jsx/main.jsx` 的函数名与返回形状不变，本轮只改 TS 侧的组织方式。
- **不引入新依赖**、不新增错误码。
- 风险：`dispatch` 与 `direct` 的默认超时不同（60s vs 30s/60s），表里没写 `timeout` 时必须按通道取默认，不能统一成 30s——否则批量操作会被判超时。

# 深模块计划 B：文档层（`repo/json-file` 加深）

> 先纠正我上一轮的错误说法：**文档层已经存在**，`repo/json-file.ts`（214 行）就是唯一入口，
> 5 个 repo 都在用（`font-set-repo` 6 处、`font-repo` 3 处、`style-repo` 2 处、`common-use-repo` 2 处、`swatch-repo`）。
> 缺的不是「文件原语 → 文档」，而是**「容错策略」还散在各个 decode 里**。

## B.1 现状

| 事 | 现在在哪 | 问题 |
|---|---|---|
| 读 → 解析 → 解码 | `json-file.ts:32-48` | 已统一 ✅ |
| 读失败不写 | `json-file.ts:71-74` | 已统一 ✅ |
| 原子写 + `.bak` | `core/storage:190` | 已统一 ✅ |
| 同一文件串行 | `json-file.ts:90-98` | 已统一 ✅ |
| **顶层数组里有一项不是对象** | `json-file.ts:201-211` `decodeRawRecords` | **整份拒绝** |
| **某一项字段缺失/类型不对** | 各 repo 的 `decode` 自己写 | 有的过滤、有的整份拒、有的用默认值 |
| **丢弃了什么** | 没有 | 页面只能显示「文件损坏」，说不出丢了哪几项 |

`sj_commonFunction.json` 第 10 项没有 `id` 导致整页 `CORRUPT`，就是第五行那条策略的后果：一项坏 → 整份不可用。

## B.2 目标接口（只加不改）

```ts
// repo/json-file.ts
export interface Dropped { path: string; reason: string }
export type DropPolicy = 'reject' | 'filter';

/** 列表解码：逐项解码，按策略决定「一项坏 = 整份失败」还是「丢掉那一项」 */
export function decodeList<T>(
  raw: unknown,
  item: (value: unknown, path: string) => Result<T>,
  policy: DropPolicy
): Result<{ items: T[]; dropped: Dropped[] }>;
```

`readJsonFile` 增加可选 `onDropped?: (dropped: Dropped[]) => void`，repo 拿到后交给 store，页面用 `StateHint` 显示「N 项无法识别，已跳过」。

## B.3 迁移

| 步 | 内容 | 回退 |
|---|---|---|
| B-M1 | 新增 `decodeList` + 单测（全好 / 一项坏 + reject / 一项坏 + filter / 空数组） | 新增函数，删掉即回退 |
| B-M2 | `common-use-repo.ts:51` 换用 `decodeList(..., 'filter')` + `onDropped` → 页面提示 | 改回 `parseCommonUseFile` |
| B-M3 | `font-set-repo`（6 处）、`font-repo`（3 处）逐个换，策略**逐个显式写**（不允许默认值） | 单文件回退 |
| B-M4 | `style-repo` / `swatch-repo` 最后换 | 同上 |

## B.4 验收

- 单测：4 个用例覆盖两种策略；
- 真机：手工把 `sj_commonFunction.json` 里一项的 `id` 删掉 → 页面应显示「1 项无法识别，已跳过」，其余项照常可用（今天的行为是整页报错）；
- 反向：把文件顶层改成 `{}`（不是数组）→ 仍应整份 `CORRUPT`（结构性错误不能过滤）。

## B.5 风险

### ① `filter` 会静默丢数据

丢掉的那一项如果用户看不出来，就是新的「说谎」。→ `dropped` 必须一路冒到 UI（`StateHint` 显示「N 项无法识别，已跳过」），且**写回时先提示用户**，不能"读的时候跳过、写的时候删掉"。

### ② 写回会洗掉未知键（最危险的一条）

现在写路径用 `RawRecords`（`json-file.ts:198`，`Record<string, unknown>[]`）**原样保留未知字段**，注释写明「丢掉就会改坏用户数据」。

如果 `decodeList` 返回的是解码后的 `T[]`，再整份写回，用户文件里的未知字段就没了——**这是静默的数据损坏**，且不可逆（`.bak` 只有上一版）。

→ 约束：`decodeList` 必须同时返回 `items: T[]` **和** `records: RawRecords`（原始对象引用），写回一律用 `records`，只在"用户显式新增/删除"时才重建。B-M1 的单测必须包含这条：**未知键写入后仍在**。

### ③ 与 A 的先后

B 不依赖 A，但两者都动 `repo`/`core`，同时改会让真机定位困难。→ 先 A-M1（2 个能力），真机确认后开 B-M1，A 的 M3 与 B 的 M2 不要同一天做。
