# 0. 第一性原理

**超原版，只砍功能。** 视觉、结构、交互、文案都照原版；与原版不一致的地方只有两种合法来源：

1. **功能被砍导致的必然差异**（例：砍了回收站，就没有「回收站视图」和「还原」）；
2. **本仓硬规则不允许**（例：`STYLE` 规则 12「hover 不许变蓝」、规则 16「浮层一律浅色白底」）。

除这两类以外，任何「我觉得这样更好」都是跑偏。所有偏离集中在 §4 一张表里，逐条给原因；表外的部分必须能与原版逐项对齐。

# 0.5 主线：存 → 看 → 应用（用户只感知这三步）

判据：**用户在这条线上任何一步问出一个问题，我们要么已经答了，要么明确不做。**

## 0.5.1 三步九个动作

| 步 | 用户动作 | 用户心里的问题 | 我们给什么 | 落点 |
|---|---|---|---|---|
| 存 1 | 选中图层 / 组，点存 | 「存到哪个文件夹？」 | 面包屑当前层就是目的地；根目录也允许 | 页面状态 `currentFolderId` |
| 存 2 | 同上 | 「叫什么名字？」 | 默认取图层名，**不弹输入框**（弹了就变成两次动作）；不满意事后右键改名 | `item.name` |
| 存 3 | 同上 | 「存哪了？成了吗？」 | 新条目高亮 2s + 滚进视口；失败才 toast（带原因） | §5.2 增益 1 |
| 看 1 | 进页面 | 「我有多少东西、在哪一层？」 | 面包屑 + 子文件夹格（带条数）+ 底栏「共 N 个内容」 | 面包屑 / `FolderCard` / `BottomBar` |
| 看 2 | 扫一眼 | 「这张是不是我要的？」 | 缩略图（vendor 生成的那张，列表里缩小显示）+ 名称 + `title` 里有尺寸 | `TemplateCard` |
| 看 3 | 看不清 | 「放大看看」 | hover 出眼睛 → 大图（按窗口最大）；`Esc` / 点空白关 | `ImagePreview` |
| 应用 1 | 点卡片 | 「贴到当前文档里去」 | vendor `mb_useTemplate`：置入当前文档；历史组由 dispatch 通道给 | §3.4 / §9.6 |
| 应用 2 | 看一眼画布 | 「成了吗？」 | 不弹 toast；成了就是画布上出现、`Ctrl+Z` 能整体撤回；失败才 toast | §0.5.2 第 2 条 + §5.2 |
| 应用 3 | 再点下一个 | 「能连续试吗？」 | 能：不跳页、不清空、不弹确认 | §5.1 |

## 0.5.2 主线带出的五条契约（每条都是「不写下来就会写错」的）

1. **「存」= 复制，不是链接。** 存入时把选中图层复制到一个**新文档**再存成 PSD；库里那份与用户原文档从此无关（原文档后续改动不影响库，库里改也不影响原文档）。
   判据：链接式会在「原文档关掉」时变成空壳，而库里必须有能长期存在的实体文件。
2. **「应用」的撤销组由通道给，不自己写。** 原版 `mb_useTemplate` 走的是 `jsxHistory`（dispatch）通道，label 就是「应用模板」（`app.v4.js:30701`）—— `ps_onJsx` 调度器本身把这次调用包成一个历史组。
   ⇒ 能力表里 `channel: 'dispatch'`，**不在 jsx 里写 `suspendHistory`**（写了就是第二套撤销语义）。一句 `Ctrl+Z` 撤回整次应用。
3. **「应用」的复制范围写死**：PSD 的**全部顶层图层**（组保持组），保持名称与层级，居中放置到当前文档；不复制参考线 / 切片 / 图层复合。
   判据：只复制「一个智能对象」会让组结构丢失；复制「整份合成」会带上背景。顶层图层是唯一能解释的边界。
4. **「修改」= 直接改库里的那一份。** 右键「编辑源文件」用 vendor `mb_openTemplatePsd` 把 `PSD/<id>.info/<file>.<ext>` **本身**打开（不是临时副本、不另存回），用户在 PS 里保存即写回库文件。
   后果必须写明：**PSD 不在 `.bak` 的保护范围内**（`.bak` 只管我们写的那份 `index.json`，且不为它做任何按钮），改坏了没有回滚 —— 只能删掉这条重新存一条。
5. **「更新预览图」只做一件事**：vendor `mb_amendPreview` 覆盖同名 png，页面随后**破缓存**（换 `?t=` 随机参数，照原版 `:27079`）。
   **不写索引**：vendor 无返回值，宽高不变；改了画布要更新尺寸，就重新存一条（不另开一条"刷新尺寸"的路）。
   前提：PSD 必须已保存到磁盘（vendor 读的是磁盘文件）—— 我们检测不了，只在菜单 `title` 提示。

## 0.5.3 主线之外的支撑（用户不会第一眼想到，但缺了就卡住）

| 类 | 功能 | 缺了会怎样 |
|---|---|---|
| 分类 | 新建 / 进返 / 重命名 / 删除空文件夹、移动条目 | 东西一多就找不着；存错位置救不回来 |
| 维护 | 重命名条目 | 名字只能靠图层名 |
| 修复 | 编辑源文件 + 更新预览图 | 库是死的；改完还是旧样子 |
| 找文件 | 打开库目录 | 用户不知道 PSD 在哪，没法备份 / 迁移 |
| 止损 | 删除条目 | 误存清不掉，只能手改坏索引 |

## 0.5.4 主线附近「看着该有、但明确不加」的

| 候选 | 为什么不做 |
|---|---|
| 大图里再放一个「应用」按钮 | 应用只留一个入口（卡片单击）；两个入口 = 两条线 |
| 存入时弹框命名 | 会把「一次点击」变成三次；改名走右键 |
| 记住上次所在文件夹（prefs） | 多一个偏好键 + 一个「文件夹可能已被删」的归一判据；文件夹只有 3–5 个 |

| 存之前预览缩略图 | 缩略图是 PS 导出的产物，存前拿不到 |
| 「最近使用」区 | 又一个列表 + 一份排序规则 |
| 同名提示 / 自动加序号 | 允许同名（`id` 不同）；加序号要多一套命名规则 |

## 0.6.1 备份模型：复制粘贴就是备份（由此产生三条设计约束）

用户要的备份是**最简单的**：把 `template` 这**一个文件夹**整个复制走，就完成了备份；换机器再粘回来，就完成了恢复。
没有导出、没有导入、没有云、没有版本历史 —— 因为库本身就是磁盘上的普通目录。

这条裁定反过来约束数据结构（不满足这三条，复制粘贴就不再是完整备份）：

| # | 约束 | 违反会长什么样 |
|---|---|---|
| 1 | **索引里禁止出现绝对路径**。`items` 只存 `id / file / ext / name / folderId / width / height / createdAt`；位置由 `id` + `file` + `ext` 推导，不存路径本身 | 存了 `C:/Users/xinye/...`，换机器 / 换用户名后整库全指向不存在的路径 |
| 2 | **自包含**：库需要的一切（索引 + PSD + 缩略图）都在 `template` 一个目录里，不引用外部文件、不引用官方 `PSDTemplate.pszhuli` | 缩略图放在别处 / 引用原文档 → 复制一半，粘过去就是破图 |
| 3 | **单目录平铺**：`index.json` + `PSD/<id>.info/` 两层，不再按文件夹拆分索引或另开目录 | 拆开后「复制哪个」变成用户要判断的事，备份必然漏东西 |

因此「打开库目录」不是可选便利，而是这套备份方案的**唯一入口**：
用户得先能找到那个文件夹，才谈得上复制。页脚同时显示绝对路径（`userSubPath('Maomao','template')`），两头都给出。

已知边界（写清，不假装兜住）：
- 只拷 `PSD/` 不拷 `index.json`（或反过来）= 索引与文件对不上；**我们的代码不修它**，库内 `README.md` 写了让 AI 对齐的办法（§3.5）。
- 两个库的 `PSD/` 手工合并 → 索引里没有这些条目，同上，照 README 补。

# 3. 数据结构（我们的，不是原版的）

## 3.1 文件放哪

```
%APPDATA%\Maomao\template\           ← core/storage 的 'data' 根（ROOTS.data = '/Maomao'）+ template
├─ index.json                        ← { version: 1, folders: [], items: [] }（**我们写**，唯一索引）
└─ PSD/<id>.info/                    ← **vendor 建**（`ps_mbAddPsd` 内部写）
   ├─ <file>.<ext>                   ← 源 PSD（`file` = 存入时的图层名，记在索引里，永不改）
   └─ <file>.png                     ← 缩略图（vendor 按源文件名生成）
```

三个事实决定这个形状（都来自原版调用点，不是猜的）：

1. `ps_mbAddPsd` 的入参只是**一个目录**，它自己在里面建 `<id>.info/`、写源文件与缩略图，并把条目的 `id / name / ext / width / height / size / time` 一起返回（`:66538` + `saveToMyTemp` `:66608`）。
   ⇒ 我们**不建文件、不生成 id、不读尺寸**；`index.json` 只记「谁、放哪个文件夹」。
2. `info.json` 在原版里是**前端写的**（`u.a.write(getFileJsonInfoPath(id), …)`），不是 vendor 写的 ⇒ 我们不需要它，索引统一在 `index.json`（见 README 的修复规则）。
3. `mb_amendPreview([<id>.info 目录, file, ext])` 与 `mb_openTemplatePsd([<id>.info/<file>.<ext>])` 都要**目录/文件路径**，由 `templateDir(id)` + `file` + `ext` 推导 ⇒ 索引里**不存任何路径**，只存这三个可推导的字段。
   `file` 是**存入时的图层名**（vendor 返回的 `name`），从此不再变；右键「重命名」只改显示名 `name`，磁盘文件不动 —— 原版 `updataName` 也只是重排瀑布、不碰文件名（`:30281`）。

1. **路径常量只有一处**：`repo/template-repo.ts` 的 `TEMPLATE_INDEX` + `templateFile(id)` / `templateThumb(id)`；命令层、store、页面都不许手写 `'template'` / `'files'`。
2. **目录谁来建**：`index.json` 的父目录由 `writeTextAtomic` 内部 `mkdirSync(recursive)` 建（`src/core/storage/index.ts:119`）；`PSD/<id>.info/` 及其中的文件由 **vendor `ps_mbAddPsd` 自己建**。前端**不建任何目录**（它只写 `index.json` 与 README）。
3. **首次创建只在用户动作时**：进页面见 `NOT_FOUND` ⇒ 空库、不写盘（`CONVENTIONS` §4.5 / §4.6）。
4. **位置不可换**；迁移 = 「打开库目录」复制整个 `template` 文件夹；页脚显示 `userSubPath('Maomao','template')`。
5. **不放 `SheJiZhuLi`**：那是官方数据目录（只读），混写会污染官方库；原版 `PSDTemplate.pszhuli` 我们**一个字节都不写**。

索引形状：`folders` 扁平表 + `parentId`（移动只改一个字段）；`items.folderId: string | null` 单归属（原版 `folder: string[]` 多归属会让「删文件夹时条目去哪」多一个分支）；改名只改 `name` 不动磁盘文件名；`version: 1` 不认识就 `CORRUPT`，不静默迁移。

两条唯一性规则（`domain` 里判，调用点不许各判一次）：
- **同一父级下文件夹名唯一**：`addFolder` / `renameFolder` 冲突返回 `VALIDATION`（`detail` 给重名与被撞的父级）。判据：两个同名文件夹在面包屑里无法区分。
- **条目名允许重复**：`id` 区分；不自动加序号（那要多一套命名规则）。

## 3.2 索引：谁读、何时读、谁写、何时写

**直接读 JSON 吗**：是，一次读全量（几十 KB）。页面与组件不碰文件，只读 store 投影，唯一读入口 `repo.readIndex()`。

| 场景 | 谁读 | 结果 |
|---|---|---|
| 进页面 / 手动刷新 | `store.load()` → `repo.readIndex()` | 成功覆盖；失败**保留上一份** + `failure` |
| 任一写命令成功后 | 命令把新索引返回给 store 回填 | **不重读文件**（少一次 IO、无「写完→读回」窗口） |
| 不存在 | `readJsonFile` → `NOT_FOUND` → `emptyTemplateIndex()` | 空库，不写盘 |

**谁写**：只有 7 个写命令（saveSelection / deleteItem / renameItem / moveItem / createFolder / renameFolder / deleteFolder），全部走 `repo.updateIndex(mutator)` = `json-file.updateOrCreateJsonFile(...)`：读 → mutator 改 → 写回（`.bak` + 原子替换）。mutator 里不许 await、不许 IO，只做 `domain` 的纯数组操作；返回 `null` = 不写。

**不互相覆盖**：同文件靠队列键 `mutate:data:template/index.json` 串行（`src/repo/json-file.ts:106`）；PS 侧只写二进制、**从不碰 index.json** ⇒ 索引只有一个写者；不缓存、不防抖（防抖合并会丢更新）。

**谁先谁后**（原则：宁可孤儿文件，不要破图）

| 动作 | 顺序 | 失败后果 |
|---|---|---|
| 存入 | jsx 先写 psd + png（都成功才返回）→ 写索引 | 索引没写成 = 孤儿文件，不破图 |
| 删除 | **先写索引**再 `removeFile` × 2 | 文件没删掉 = 孤儿文件，无害 |
| 更新预览图 | jsx 覆盖 png → 索引不用改 | 覆盖失败 = 旧图 + 报错 |

**索引什么时候不更新**（页面要诚实）：用户手删/改名文件我们不知道（应用时 `NOT_FOUND`）；手改 `index.json` 就按新的读，解码不过整库 `CORRUPT` 且不覆盖；缩略图缺失只 `.mm-notice` + 右键「更新预览图」，不自动重建。

三条不许：

- **不写 `jsx/main.jsx` 的对应函数**：这五个 vendor 已有，自己再写一遍 = 同一能力两条路（`ADR-0005`）。
- **`place` 与 `open` 不合并**：一个置入当前文档、一个开新文档，语义不同；合成带 `mode` 的函数就是把两种写法请回来。
- **`cy_openDirectory` 不复用**：它无参、只开「当前文件所在目录」，与「打开指定库目录」不是一件事（文件头写明区别）。

命名撞车（实现时会遇到）：`core/ps/template.ts` 的前端薄函数名与 `commands/template.ts` 的命令可能同名。
照 `commands/common-use.ts` 既有写法：命令层 `import { openLibraryDir as openLibraryDirJsx }` 之类加 `Jsx` 后缀，不另起第二套业务名。

## 3.5 索引坏了怎么办：**我们不做修复功能，写一份 README 让 AI 修**

用户的原话：索引乱了不该变成我们的一个功能按钮，而是库目录里放一份说明，用户照着让 AI 修就行。
所以**没有任何修复入口**：没有「重建索引」按钮、没有 `scan` 能力、没有回滚按钮。只有一份随库落盘的 `README.md`。

要成立，README 必须把「修复所需的一切」写全 —— 否则用户拿给 AI 也修不了。README 的内容规格（这就是它的验收标准）：

| 段 | 写什么 |
|---|---|
| 这是什么 | 一个模板库的数据目录，PS 面板读写它；`PSD/` 下每个 `<id>.info/` 是一条模板（里面一个源 PSD + 一个同名 png），`index.json` 是**列表用的索引**（可以重建，不影响 PSD） |
| 备份 / 迁移 | **复制整个 `template` 文件夹**即完整备份；粘回即恢复。不要只拷 `PSD/`（会和索引对不上） |
| 索引坏了会看到什么 | 列表空白但 `PSD/` 下有条目目录；破图；点开报「文件不存在」；面板提示内容无法识别 |
| 怎么修（给 AI 的指令） | 「读 `index.json`，把它与 `PSD/` 下实际的条目目录对齐，重写索引」，并附下面这份 schema 与三路合并规则 |
| schema | `{ version: 1, folders: [{ id, name, parentId }], items: [{ id, file, ext, name, folderId, width, height, createdAt }] }`；**位置一律由 `id` / `file` / `ext` 推**（`PSD/<id>.info/<file>.<ext>` 与同名 `.png`），索引里不存路径。`file` 与 `name` 分开：`file` 永不变、`name` 随便改 |
| 合并规则 | 以 `PSD/` 下的目录为条目单位：目录在 + 索引有 → 留；目录在 + 索引没有 → **新增**（`id` = 目录名去掉 `.info`；`file` / `ext` = 目录里源文件的主干与扩展名；`name` 初始取 `file`；`folderId = null`；`createdAt` = 源文件 mtime 的**毫秒数**）；索引有 + 目录没有 → **删该条**；目录里没有源文件（只剩 png）→ 跳过并报告 |
| 不许做什么 | 不要重命名 `PSD/<id>.info/` 目录（**目录名就是条目 id**）；不要改里面源文件的文件名（**它的主干就是 `file` 字段**，改了路径就断）；不要删 PSD（那才是真数据）；`folderId` 指向不存在的文件夹时归 `null`；`name`（显示名）随便改，与路径无关 |
| 兜底 | 实在修不好：`PSD/` 下的 PSD 都是完整文件，拷出来即可，重新「存入」一遍 |

**落盘时机**：只在**库目录可能刚被创建**那三处调 `ensureReadme()` ——「存入」「新建文件夹」「打开库目录」。
改名 / 移动 / 删除不调：库早就存在，README 也在，调了只是一次无意义的 `exists`。
`ensureReadme` 幂等（先 `exists`，在就什么都不做），所以最坏是「一次 stat」，不是每次重写。
写失败只 `log.warn`，不影响业务；`README.md` 不是库的必需文件（删了不影响读写）。

**这条为什么是对的**：`index.json` 是纯派生数据（`id` 从文件名来、其余字段要么来自文件本身、要么是人为分组），
所以「修复」本质是一次**数据整理**，不是业务流程。把它写进 README 交给 AI 现场做，比写一个只覆盖 80% 情况的扫描器更彻底。

## 5.3 右键菜单（定稿，就这些，没有第 7 项）

**条目卡右键** —— 6 项，两级分组，删除放最后并标红：

| # | 菜单项 | 行为 | 反馈 |
|---|---|---|---|
| 1 | 重命名 | `InputDialog` 输入新名 → 改 `item.name`（不动磁盘文件名） | 列表即时更新；失败 toast |
| 2 | 编辑源文件 | 打开 `PSD/<id>.info/<file>.<ext>` **本身**（vendor `mb_openTemplatePsd`），用户在 PS 里直接改、保存即生效 | 不弹窗；失败 toast |
| 3 | 更新预览图 | vendor `mb_amendPreview` 重建缩略图；命令只返回 `Result<void>`，**页面随后 bump 图片版本号**（`?t=<n>`，§9.8 `imageVersion`） | 成功 toast 一句；`title` 提示「改完记得先在 PS 里保存」 |
| ─ | （分隔线） | — | — |
| 4 | 移动到… | 弹层**只列根层**；hover 到有子级的文件夹上，从右侧弹出下一层（再深再弹）；点任意一层即移进去 → 改 `folderId` | 从当前层消失；目标层出现。**不平铺进菜单**：菜单项数=文件夹数，10 个就溢出（`ContextMenu` 不能滚）（2026-10-31 两改：先平铺，用户指出会太长，定为级联） |
| 5 | 打开库目录 | vendor `Fs_openFolder` → 系统文件管理器打开 `%APPDATA%\Maomao\template` | 失败 toast（带路径） |
| 6 | 删除 | `useConfirm()` 一次确认 → 先写索引再删两个文件 | 列表移除；失败 toast |

**文件夹格右键** —— **2 项**：`重命名` / `删除`（仅空文件夹可点；非空置灰）。
**没有「新建子文件夹」**（2026-10-31 用户裁定）：建文件夹只有**一个入口** —— 在内容区**空白处右键** → `新建文件夹`，建在**当前这一层**。
判据：一处能建就不给第二个入口；右键某个文件夹上「新建」会让人以为是建在它里面（实际建在哪层还要靠面包屑判断），不如统一按「当前位置」建。

**更新预览图之后必须破缓存**：`mb_amendPreview` 覆盖的是同一个 `<file>.png`，`<img src>` 不变就不会重载 —— 原版的做法是**换地址后面加随机查询参数**（`:27079` `getFilePreviewImgPath(...) + "?t=" + Math.random()`）。
我们照做：命令成功后把该条目的图片地址换成 `…?t=<Date.now()>`。
**不做「未保存检测」**：vendor 函数读磁盘文件，我们无法在调用前问 PS「这个文档存没存」（`core/ps` 没有这个能力，为一个提示加一条能力不划算）。改为 `title` 文案提示，不替用户保存。

**其余右键项一律不加**：新建设计稿、导出素材包、导出到计算机、文件夹图标、评分、标签、恢复（回收站）—— 功能已砍，菜单里也不留灰项（灰项是无功能承诺）。

三条实现约束（防止下一个人写歪）：

1. **`updateIndex` 必须把写后的索引返回给调用方**：`json-file` 只回 `Result<void>`，所以 repo 在 mutator 里留住 `next`，成功后 `ok(next)`。

### 9.6.1 照着现有体系写：五行原文（不许另建一套）

既有四步全在 `core/ps/capability.ts`（门 → `funcMissing` → 前置 → `toWire` → `parse`），`gate` 与 `channel` 是**判别联合**（`{gate:'vendor', channel}` 才有 `label`；`{gate:'core'}` 只能 `direct`）。所以本页只往 `capabilities.ts` 加五行，**不动执行器、不加第三个通道、不写新的解析器**。

```ts
/** `ps_mbAddPsd` 的载荷校验：照 `fontsOf` 的写法，只判结构、不判语义（语义在 domain 判） */
function addedTemplateOf(data: unknown): AddedTemplate | null {
  if (!isRecord(data)) return null;
  const { id, name, ext, width, height } = data;
  if (typeof id !== 'string' || !id) return null;
  if (typeof name !== 'string' || typeof ext !== 'string') return null;
  if (typeof width !== 'number' || typeof height !== 'number') return null;
  return { id, name, ext, width, height };
}

// ↓ CAP 里这五行，逐字段照邻居写（字段含义见 capability.ts 文件头）
templateAdd:     { fn: 'ps_mbAddPsd',       gate: 'vendor', channel: 'direct',   timeout: WRITE_TIMEOUT,
                   require: () => requireSelection(1),
                   parse: strictPayload({ whenFalse: MSG.template.noSelection,
                                          whenFailed: MSG.template.saveFailed,
                                          accept: addedTemplateOf }) },
templateThumb:   { fn: 'mb_amendPreview',   gate: 'vendor', channel: 'dispatch', timeout: WRITE_TIMEOUT,
                   parse: lenientVoid(MSG.template.thumbFailed) },
templateUse:     { fn: 'mb_useTemplate',    gate: 'vendor', channel: 'dispatch', label: '应用模板',
                   timeout: LONG_TIMEOUT, parse: lenientVoid(MSG.template.useFailed) },
templateOpen:    { fn: 'mb_openTemplatePsd', gate: 'vendor', channel: 'direct',  timeout: WRITE_TIMEOUT,
                   parse: lenientVoid(MSG.template.openFailed) },
templateOpenDir: { fn: 'Fs_openFolder',     gate: 'vendor', channel: 'direct',   timeout: WRITE_TIMEOUT,
                   parse: lenientVoid(MSG.template.openDirFailed) },
```

四条照抄纪律：

1. **`parse` 只许引用 `core/ps/raw.ts` 的具名解析器**（这里用 `strictPayload` / `lenientVoid`），不在薄函数里再判一次返回结构 —— 严格度是能力的契约，写在表里一眼能看见。
2. **`label` 只在 dispatch 用**，会变成 `ps_onJsx` 的 `n`（日志标签）；`应用模板` 与原版一致（`:30701`）。
3. **薄函数只做语义包装**（`addTemplate(dir)` → `callCapability(CAP.templateAdd, [dir])`），不写门、不写超时、不写解析 —— 照 `core/ps/rename.ts` 的两行体量。
4. **`AddedTemplate` 用 `import type`** 引到 `capabilities.ts`（`core/ps/template.ts` 定义），type-only 不产生运行时循环。`whenFalse` / `whenFailed` 一律取 `MSG.template.*`，**不仿 `core/ps` 里那 29 处中文存量**（`TD-04-1`）。

**中文放哪：按用途分两处，没有「禁止中文」这条规则**

| 这类中文 | 放哪 | 本页例子 |
|---|---|---|
| 系统**告诉用户发生了什么**（失败 / 成功 / 确认 / 空态 / 进度 / 输入校验） | `MSG`（`types/messages.ts`，生产者取、消费者不补字） | 「模板保存失败」「文件夹名重复了」「这个文件夹不是空的」 |
| 界面**自己的名字与标签**（按钮 / 菜单项 / 字段 `title` / 占位符 / 分组名） | **就地写在页面或组件里**，不进 `MSG` | 「新建文件夹」「重命名」「从选中图层存入」「共 N 个内容」 |

`MSG.template` 需要的**键**（键名是契约，文案实现时按 `MSG` 文件头那一条判据写）：
`noSelection` / `saveFailed` / `thumbFailed` / `useFailed` / `openFailed` / `openDirFailed` / `folderNameTaken` / `folderNotEmpty` / `badName`；
通用码直接复用既有键，不新造：`MSG.corrupt`（结构认不出）、`MSG.codeReason.NOT_FOUND`、`MSG.codeReason.IO_ERROR`、`MSG.codeReason.VALIDATION`。
`core/ps` 里那 29 处中文存量（`TD-04-1`）是**位置错**（生产者在 `failWithDetail` 里自己造句），不是"中文不该存在"—— 新写的一律从 `MSG` 取，存量不追溯。

```
失败：vendor 已写目录、索引未写 ⇒ 孤儿目录（无害，README 的合并规则能捡回来）。**id 不由我们生成**（vendor 给）
```

**删条目**

```
页面 → commands.deleteItem(id)
  → repo.updateIndex(idx => domain.removeItem(idx, id))   // 先写索引
  → repo.removeItemDir(id)                                // 再删整个 <id>.info/ 目录（core/storage.removeDir）；失败只 log.warn
  → store.applyIndex(next)
```

**更新预览图**

```
页面 → commands.refreshThumb(id)
  → core/ps/template.rebuildThumb(templateDir(id), file, ext)   // vendor mb_amendPreview（dispatch）；传 file
  → 页面本地 bumpImage()：拼 <img src> 时加 ?t=<版本号>（破缓存，照原版 :27079）
  → **不写索引**（vendor 无返回值，宽高不变；改了画布要更新尺寸就走「重新存入」）
```

## 9.10 层间传递不丢字段（刀 14 自查）

# 11. 未验（不许当已验证）

> **这一节只有「验收时看一眼」的条目，没有「不探完不敢写」的条目。**
> 五个动作全是 vendor 已有函数（§3.4），照调用契约写即可；函数体是 jsxbin，本来也看不到。

1. `ps_mbAddPsd` 返回的 `data` 是否**恒含** `id / name / ext / width / height`（我们 `strictPayload` 只认这五个；少一个就落 `PS_BAD_PAYLOAD`，不会静默错）。多出来的字段（`size/star/tags/note/adjustY/find/time`）不存。
2. `mb_useTemplate` 的载荷字段够不够：原版载荷是 `Object(ft.c)(showList[t])` + `path` + `useTmeplatePadding` + `status`（`:30697-30705`），`ft.c` 的字段全貌未提取（`TPL-01`）。不够时**只补字段，不换入口**。
3. `mb_amendPreview` 是否同步完成：原版调用后 `setTimeout(…, 100)` 才换图（`:27079`），说明它可能异步。我们的破缓存照做了，但首次仍可能取到旧图 —— 真机看一眼是否需要把等待拉长。
4. `mb_useTemplate` 的 `status` 三支（1 / 2 / 0，`:30707-30737`）分别对应「有选中文档 / 无文档 / 其它」，我们固定传哪个要在 M3 真机确认一次（先按 `status: 1` 走）。
5. 撤销粒度：dispatch 通道给的是一个历史组；真机 `Ctrl+Z` 一次是否只撤这一步。
6. **缩略图尺寸我们控制不了**：`ps_mbAddPsd` 内部决定尺寸。放大到大图后够不够清只能真机看；不够的话只有两条路 —— 要么接受，要么自己写一个重出缩略图的 jsx（那等于加第六个能力，要重新裁定，不许偷偷加）。
7. 透明底 PNG 落在 `--mm-color-bg-input` 上是否可读。
8. 索引并发（`json-file` 队列保证同文件串行，但无可靠单测）。
9. **原版图标名未提取**（`IconFont` 是字体图标，`glyph` 名未反查）⇒ §6 是语义映射，不是原版同名。
10. **非 ASCII 文件名**：`<file>.png` 的 `file` 来自图层名（中文字幕常见），`userAssetUrl` 逐段 `encodeURIComponent` 是否足以让 `<img>` 显示（`file://` + 中文是已知易错区）。
