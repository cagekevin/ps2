# 14 · PS 失败语义收口

> **状态：已实施（2026-10-30）** —— 四步全部落地，验收数字见 §四；`TD-01-18` / `19` / `20` 已关闭。
>
> 目标：**一个失败语义只有一个码、一句话、一个构造点**。
> 起因：应用字体已换好，toast 报「文件无法识别」——解析器在猜，不是宿主在失败。
> 关联：`ADR-0003`（同一个失败只变形一次）、`ADR-0005`（旧的删不掉就别加新的）。
> 债：`TD-01-18` / `TD-01-19` / `TD-01-20`（登记于 `daily/架构日志/01-跨区-解析器失败语义-2026-10-30.md`）。

---

## 一、现状

### 1.1 形状地图

**形状只有一个**（这点是好的）：

```ts
// src/types/result.ts
type Result<T> =
  | { status: 'ok'; value: T }
  | { status: 'error'; code: ErrorCode; reason: string; detail?: string };
```

构造点也只有一个文件（`result.ts` 的 `ok` / `fail` / `failWithDetail`）。

**但失败臂的 `reason` 有 5 种口径**，同一个码在不同层说不同的话：

| # | 口径 | 例子 | 出现处 |
|---|---|---|---|
| 1 | `MSG.codeReason[code]`（标准话） | 「PS 执行失败」 | `bridge:95`、`raw:58`、`unwrapRaw:39` |
| 2 | 宿主原话 | 「请选择文字图层」 | `lenientVoid:233`、`bridge:164` |
| 3 | 能力自带文案 | `whenFailed` / `fallback` | `strictPayload:279/284`、`lenientVoid:233` |
| 4 | 自由文本 | 「标签名不能超过 8 个字」 | `commands/font.ts:130` |
| 5 | 通道专用话 | 「返回数据无法识别」 | `lenientVoid:226/237` |

### 1.2 契约（现状）

| 契约 | 定义处 | 现状问题 |
|---|---|---|
| `Result<T>` | `types/result.ts` | ✅ 单形状、单构造点 |
| `Parser<T>` | `core/ps/raw.ts:186` | 5 个具名解析器，**「认不出」有 4 处各自构造** |
| `CapabilitySpec<T>` | `core/ps/capability.ts` | `parse` 字段是唯一选择点 ✅，但选谁没有判据表 |
| `ErrorCode` | `types/result.ts` | `PS_ERROR` **同时装两种语义**：执行失败 / 返回认不出 |

### 1.3 数据流（七步，失败可能在任一步落地）

```
① features        点色块 / 点字体
        ↓  （参数：磁盘原始项）
② commands        拍平、校验范围（46 处 fail*）
        ↓
③ capability      四步固定：gate → require → channel → parse
   ├ gate         requireVendor() 失败 → PS_UNREADY  detail:vendor:false
   ├ require      requireTextLayer 失败 → PS_WRONG_LAYER  detail:kind:xxx
   ├ channel      direct: callJsx(fn,args) ／ dispatch: callJsx(ps_onJsx,{f,arr,n})
   └ parse        raw(string) → Result        ← 本计划的落点
        ↓
④ bridge          evalScript
   ├ 无桥        → PS_UNREADY  detail:bridge:no-cep
   ├ 超时        → TIMEOUT     detail:evalScript:…
   └ 宿主抛异常   → PS_ERROR    detail:evalScript:… ／ reason:宿主原话
        ↓
⑤ jsx             ExtendScript，返回字符串（`undefined` / `1` / `{"err":0,…}` / `{"code":"OK"}`）
        ↓
⑥ 回程            Result 原样透传，commands 不重包
        ↓
⑦ 消费            useRunCommand → toast.error(reason) + log.warn(code, detail)
```

**失败语义跨 5 层，构造点分布（实测）**：

| 层 | 构造点 | 它管的事 |
|---|---|---|
| `bridge.ts` | 7 | 通道 |
| `init.ts` | 3 | 门（透传，不新造） |
| `capability.ts` | 5 | 前置 |
| `raw.ts` | 13 | 宿主返回的翻译 |
| `commands/*` | 46 | 业务校验 |

## 二、目标形状

**失败只有三类语义 + 一张约定值表**，每类一个构造器、一个码、一句话：

| 语义 | 构造器 | 码 | reason | detail |
|---|---|---|---|---|
| 宿主返回**认不出** | `unrecognized(raw)` | `PS_BAD_PAYLOAD`（新增） | `MSG.badPayload`「返回数据无法识别」 | `raw:…`（截 120 字） |
| 宿主**明确拒绝**（`err:1`） | `hostRejected(value, raw, fallback)` | `VALIDATION` | 宿主 `msg`，没有才用 fallback | `raw:…` |
| 结构**认得出但字段坏** | `malformed(detail)` | `CORRUPT` | `MSG.corrupt`「文件无法识别」 | 字段路径 |
| 约定值（`no-doc`/`-1`/…） | `unwrapRaw`（不动） | 表里那个码 | `MSG.codeReason[code]` | `raw:…` |

**关键决定：新增 `PS_BAD_PAYLOAD`，不再借 `PS_ERROR`。**
`PS_ERROR` 现在同时表示「执行失败」和「返回认不出」，是「一个名字装两种语义」；
分开后 `PS_ERROR` 只剩执行/通道失败，`PS_BAD_PAYLOAD` 只表示「我们看不懂宿主说的话」。

### 2.1 深模块与门面

`raw.ts` 已经是**深模块**（外部只需要「给我一个解析器」），问题是**门面没分类、构造器会外溢**。
目标门面按用途分四组，**三个构造器一个都不导出**：

| 组 | 导出 | 谁用 | 现状引用数 |
|---|---|---|---|
| 解析器工厂 | `lenientVoid` / `strictData` / `strictPayload` / `sentinelJson` / `parseDataEnvelope` / `passthrough` / `Parser` | `capabilities.ts` 的 `parse` 字段 | 41 / 2 / 7 / 2 / 3 / 6 |
| 专用解析器 | `parseFontFamily` / `parseSystemFontList` / `parseErrEnvelope` | 字体三处、样式一处 | 4 / 8 / 2 |
| 组合逻辑原语 | `parseJsxRaw` / `unwrapRaw` / `envelopeMessage` | **只有** `font.ts` / `style.ts` / `diag.ts` 写多步逻辑时用 | 6 / 34 / 2 |
| **私有（不导出）** | `errOf` / `dataOf` / `isOkSentinel` + 三个构造器 | 模块内部 | **0 / 0 / 0** |

**净变化：导出 17 → 14**（私有化 3 个零引用导出：`errOf` / `dataOf` / `isOkSentinel`），构造器 3 个全部私有。
`parseJsxRaw` / `unwrapRaw` **必须留**：`font.ts` 的「先 check 再 apply」、`style.ts` 的 `saveLayerStyle` 是多步组合，不是单能力，塞不进能力表。

### 2.2 四条边界（必须写死，否则又长两套「看不懂」）

| 情况 | 判 | 判据一句话 |
|---|---|---|
| 信封本身不是我们认识的形状（不是 JSON / 没有 `err` 字段） | `PS_BAD_PAYLOAD` | **信封坏** |
| 信封对、里面的载荷不是约定形状（`data.fonts` 不是数组、缺 `family`） | `CORRUPT` | **载荷坏** |
| `err:1`（宿主明确说没成功） | `VALIDATION` | **宿主拒绝**，原因优先宿主 `msg` |
| `false`（图层类型不适用） | `VALIDATION` | **条件不满足**，不是失败 |

## 三、四步落点（顺序不可换：先有码，才有构造器）

### Step 0 · 新增 `PS_BAD_PAYLOAD` 码

| 文件 | 改动 |
|---|---|
| `types/result.ts` | `ErrorCode` 加 `'PS_BAD_PAYLOAD'`；文件头注释写清与 `PS_ERROR` 的分工 |
| `types/messages.ts` | `codeReason` 是 `as Record<ErrorCode, string>` **全量映射**，加码必须加表项（否则编译红）。它与 `MSG.badPayload` 同义 → 提取模块级常量 `const BAD_PAYLOAD = '返回数据无法识别'`，两处都引用它，**字面量只写一次** |
| `components/StateHint` | 确认它不在「前提类码灰字」名单里（它是通道类，应标红，默认即红，不动） |

为什么排第一：Step 1 的构造器要用这个码；反过来做就得先借 `PS_ERROR`、再全局改一遍。

### Step 1 · `raw.ts` 加三个构造器 + 替换 11 处（纯结构，行为不变）

新增（`unwrapRaw` 之后，**全部私有**，不导出）：

```ts
/** 宿主返回认不出：码 / 文案 / detail 形状的唯一出处 */
function unrecognized(raw: string): Result<never>

/** 宿主明确拒绝（err:1）：文案优先宿主原话 */
function hostRejected(value: unknown, raw: string, fallback: string): Result<never>

/** 结构认得出、字段坏 */
function malformed(detail: string): Result<never>
```

替换表（行号 2026-10-30 现状；`raw.ts` 共 13 处 `failWithDetail`，动 11 处、留 2 处）：

| 行 | 现在 | 改成 |
|---|---|---|
| 58 `parseJsxRaw` 非 JSON | `PS_ERROR` + `codeReason.PS_ERROR` | `unrecognized` |
| 147 `errOf` 无 `err` 字段 | `CORRUPT` + 「文件无法识别」 | `unrecognized` |
| 226 `lenientVoid` 非 JSON | `PS_ERROR` + `badPayload`（内联） | `return parsed`（`parseJsxRaw` 内部已经是 `unrecognized`，不再包一层） |
| 237 `lenientVoid` 其它 | `PS_ERROR` + `badPayload`（内联） | `unrecognized` |
| 284 `strictPayload` 兜底 | `PS_ERROR` + `whenFailed` | `malformed('field:payload')`（信封对、载荷坏） |
| 167 `parseDataEnvelope` `err!=0` | `PS_ERROR` + 宿主话 | `hostRejected` |
| 233 `lenientVoid` `err:1` | `VALIDATION` + 宿主话（内联） | `hostRejected` |
| 279 `strictPayload` `err:1` | `PS_ERROR` + 宿主话 | `hostRejected` |
| 310 `strictData` `err!=0` | `VALIDATION` + 宿主话 | `hostRejected` |
| 79 `parseFontFamily` 缺 family | `CORRUPT` | `malformed('field:family')` |
| 112 `parseSystemFontList` 非数组 | `CORRUPT` | `malformed('shape:…')` |
| 39 `unwrapRaw` 约定值 | 表驱动 | **不动** |
| 275 `strictPayload` `false` | `VALIDATION` + `whenFalse` | **不动**（条件不满足，不是失败） |

「认不出」实际是 **5 处**（58 / 147 / 226 / 237 / 284）。上一版写的 4 处是数错了，验收按 5 算。

### Step 2 · 门面收窄（私有化 3 个零引用导出）

`errOf` / `dataOf` / `isOkSentinel` 外部引用数都是 **0**（实测），去掉 `export`；
`raw.test.ts` 里直接测这三者的用例改成经公开解析器间接断言。

导出 15 → 12，三个构造器不导出。`parseJsxRaw` / `unwrapRaw` **必须留**（组合逻辑要用）。

### Step 3 · 上层只校验，不合并

`bridge.ts`(7) / `init.ts`(3) / `capability.ts`(5) **保持各自语义**（通道 / 门 / 前置不是一回事，不该并进解析器），只做两件事：

1. 逐个确认 `reason` 来自 `MSG`、`detail` 带现场 —— 已满足，**不改代码**
2. 三个文件头各加一行判据：「本层只报通道/门/前置失败；宿主返回的翻译在 `raw.ts`」

## 五、边界（明确不做）

| 不做 | 理由 |
|---|---|
| 把 `bridge` / `init` / `capability` 的 15 处合成一个构造器 | 通道 / 门 / 前置是三类不同语义，合并会让 `detail` 丢现场 |
| 改 `commands/*` 的 46 处 | 那是业务校验（参数范围、下标越界），不是 PS 语义 |
| 给解析器加「必须来自 MSG」的 lint | 加闸被禁止（`GOVERNANCE` §六），靠文件头判据 + 代码评审 |
| 让 `strictData` / `strictPayload` / `lenientVoid` 合成一个 | 它们回答三个不同问题（严格读 / 三态读 / 写操作），只共用构造器 |

## 九、收益与风险

### 9.1 收益

| # | 收益 | 能不能量化 |
|---|---|---|
| 1 | **「返回认不出」不再被说成「文件无法识别」** —— 用户不会去修一个没坏的文件，也不会以为字体没应用（真机 2026-10-30 踩的就是这个） | ✅ 误报类型 2 → 0 |
| 2 | 排查路径唯一：`PS_BAD_PAYLOAD` 一出现就锁定「宿主返回形状变了」，不用再猜是哪层、哪个解析器 | ✅ 码 → 层 的映射从 1 对 2 变成 1 对 1 |
| 3 | 新写解析器只有 3 个构造器可选，**发明第 4 种说法的成本变高**（得自己写 `failWithDetail`，评审能看见） | ⚠️ 靠评审，不靠编译器 |
| 4 | `PS_ERROR` 从两义变一义，日志里 `grep PS_ERROR` 的结果可以直接当「执行失败」读 | ✅ 语义数 2 → 1 |

**量化不了的收益（但真实存在）**：这次从「字体假失败」查到底花了 4 轮对话；收口后同类问题应该是「看一眼码 → 看 detail 里的 raw → 定位」三步。

### 9.2 风险

| # | 风险 | 等级 | 依据 / 缓解 |
|---|---|---|---|
| 1 | **旧日志对不上**：`PS_BAD_PAYLOAD` 是新码，历史日志里搜不到 | 低 | 新码首次出现的时间点记在 `CHANGELOG`；旧日志里的 `CORRUPT`+「文件无法识别」按本文档回溯为 `PS_BAD_PAYLOAD` |
| 2 | **`raw.test.ts` 6 条断言要改**，改错会掩盖真问题 | 中 | 改的是「期望的码」，不是「期望的成败」；每条改动在 PR 里逐条说明「原来断言什么、为什么换码」 |
| 3 | `Record<ErrorCode, string>` 漏加表项 → 编译红 | 低 | 编译器直接拦，不会静默 |
| 4 | 改码影响下游分支 | **很低（已实测）** | 全仓 **0 处**按 `code === 'PS_ERROR' / 'CORRUPT'` 分支；`StateHint` 只判 3 个软码（`NOT_FOUND` / `PS_NO_DOC` / `PS_WRONG_LAYER`），新码自动标红，符合预期 |
| 5 | `parseErrEnvelope` 的调用方（`saveLayerStyle`）依赖 `errOf` | **无影响（已读代码）** | `saveLayerStyle` 只看 `status === 'error'` 就上抛，不看具体码 |
| 6 | 改到一半停在半态（就是现在这个状态） | 中 | 四步全部在一个 PR 里做完；Step 0-2 只动 `result.ts` / `messages.ts` / `raw.ts` + 一个测试文件，`git revert` 单文件级可回退 |

### 9.3 不做这个计划的代价（写出来做对比）

- 下一个「假失败」仍然要 4 轮对话才能定位（`PS_ERROR` 到底哪层报的，得逐层读）
- 新加解析器的人仍然会照抄最近看到的那种写法 —— 仓里现在有 5 种可抄
- `TD-01-18/19/20` 一直挂着，每次体检都要重新数一遍「认不出有 4 处还是 5 处」（这次就数错过一次）
