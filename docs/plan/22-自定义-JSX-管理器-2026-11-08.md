# 22 · 自定义 JSX 管理器（用户自建按钮 + 6 档作用范围）

日期：2026-11-08
状态：**规划中（阶段 1 待开工）**
目标：用户自己写一段 ExtendScript 存成按钮，按钮上带着「对哪些图层生效」的定义；点一下就按那个定义执行。读写存 + 云同步 + 一个使用页。

---

## 0. 七条裁定

1. **作用范围是定义期属性**：创建/编辑时定，随文件存，运行时没有选择器。界面不按范围分组。
2. **不绑具体图层**：没有「绑死某个图层」这种档。文字层那一档是「只对文字图层生效」（按类型过滤），因为换文档、改名、id 都留不住。
3. **6 档全部不改文档结构**：盖印 / 合并 v1 不做（见 §11）。v1 里没有任何破坏性操作。
4. **「选区」专指像素选区（蚂蚁线），与「选中的图层」是两件事**：两义同名必然被下一个人搞错（plan 18 §4.1 已裁过）。所以 scope 值里 `pixelSelection` 只指蚂蚁线；选中图层一律叫 `layers` / `textLayers` / `shapeLayers`。
5. **一个文件存全部脚本**：`custom-scripts.json`（`data` 根 = `%APPDATA%\Maomao\`），根是裸数组。不拆「每脚本一个文件」。
6. **云同步做，但 `script.custom` 是可选 unit**：老快照没有这一节时下载跳过，不报错。
7. **不做图标**：照动作页，纯文字按钮 + `mm-btn-grid` + 列数偏好 + 右键菜单。

## 2. 原语（阶段 1，先定死）

### 2.1 数据形状 `src/types/script.ts`

```ts
/** 作用范围：定义期属性，点击时按它解析目标。**唯一事实是数组**，类型从它推导 */
export const SCRIPT_SCOPES = [
  'any',            // 不指定：跑一次，脚本自己看文档
  'layers',         // 选中的每个图层
  'textLayers',     // 选中里的每个文字层
  'shapeLayers',    // 选中里的每个形状层
  'docTextLayers',  // 整个文档的每个文字层
  'pixelSelection'  // 像素选区：跑一次，必须有蚂蚁线
] as const;

export type ScriptScope = (typeof SCRIPT_SCOPES)[number];

/** 一条用户脚本；存盘形状与运行形状是同一个，没有 order 字段（顺序 = 数组顺序） */
export interface ScriptItem {
  id: string;
  name: string;
  scope: ScriptScope;
  code: string;
}

/**
 * 执行报告。**没有 `ok` 字段**：成功数 = `total - failed.length`。
 * 存两处就是两个真相（jsx 算一遍、页面再算一遍，迟早对不上）。
 */
export interface ScriptRunReport {
  total: number;
  failed: { target: string; reason: string; line: number }[];
  /** 脚本 `return` 的值（字符串化）；没有返回值就不带这个字段 */
  result?: string;
}
```

- 没有 `enabled`：v1 不做停用，删掉即停用。
- `SCRIPT_SCOPES` 用 `as const` + 类型推导，**不是**「一个数组 + 一个手写联合」：两份枚举迟早漂，而 `as const` 让漂不过编译（`ADR-0004` 级 1）。数组放 `types/` 有先例（`types/layer.ts` 的 `LAYER_KIND_LABEL`）。

### 2.2 jsx 契约 `jsx/main.jsx`

```js
/**
 * 执行一条用户脚本（唯一入口）。
 * @param scope 'any'|'layers'|'textLayers'|'shapeLayers'|'docTextLayers'|'pixelSelection'
 * @param code  用户源码（多行；到 jsx 侧是一个字符串）
 * @param label 历史面板显示名（用户给的按钮名）
 * → { total, failed: [{ target, reason, line }], result? }
 *   | 'no-doc' | 'no-target' | 'no-selection' | 'bad-scope' | 'error:…'
 */
function mm_script_run(scope, code, label)
```

**注入变量**（每个目标执行前赋好，脚本里直接用）：

| 变量 | 内容 |
|---|---|
| `layer` | 当前目标层；`any` 档 = `app.activeDocument.activeLayer` |
| `mmTargets` | 目标层数组（**所有档都有**；`any` 档 = 当前选中集合，可能空） |
| `mmSelection` | 像素选区矩形 `{ left, top, right, bottom, width, height }`（px）；**所有档都有**，无选区 = `null` |
| `mmIndex` | 当前是第几个，从 0 起 |
| `mmScope` | scope 原值 |

**为什么必须注入**：`app.activeDocument.activeLayers` 在本机是 `undefined`（`jsx/main.jsx:113` 记着这个坑，我们自己的代码已全部改走 `targetLayers`）。用户照网上抄的脚本会静默失败，且失败点极难定位。`mmTargets` 由我们解析好再给。

`mmSelection` 同理：`doc.selection.bounds` 的元素可能是 `UnitValue` 也可能是数字（PS 版本差异，`mm_px` 的注释记着真机 26.7 打印 `[{}, {}, {}, {}]`），直接 `.as('px')` 在纯数字上会抛。选区还要 clamp 到画布内、零尺寸按无选区处理。这些都由 `mm_sel_bounds` 做掉，用户拿到的已经是 px 数字。

`mmSelection` 是**执行前快照**：脚本内部自己改选区后它不会跟着变（逐层重算既慢又容易读到中间态）。要实时值就自己读 `app.activeDocument.selection.bounds`，这一点写在注入表旁边。

**返回值只有一个用途**：`eval` 的结果不是 `undefined` 时，字符串化后放进报告的 `result`。逐层档是「最后一次赋值生效」——只有 `any` / `pixelSelection` 两档适合用它输出信息。**失败不靠返回值表达**（`return false` 与 `return true` 同义，都是成功），要标记失败就 `throw`。

**目标解析**（每档 → 层数组）：

| scope | 目标 | 复用 |
|---|---|---|
| `any` | 1 个伪目标（不遍历） | `doc.activeLayer` + 选中集合 |
| `layers` | 选中集合，逐层 | `mm_layer_selectedIndexes` + `mm_layer_walkIndexOrder` |
| `textLayers` | 选中集合 ∩ `mm_layer_kindOf === 'text'` | 同上 |
| `shapeLayers` | 选中集合 ∩ `mm_layer_kindOf === 'shape'` | 同上 |
| `docTextLayers` | 全文档摊平 ∩ text | `mm_layer_walk` |
| `pixelSelection` | 不遍历，跑一次；`mmSelection` 必须非 null；`layer` = `doc.activeLayer`（不切换） | `mm_sel_bounds` |

- 空目标 → `'no-target'`；**`any` 档永不空**（它永远跑一次，哪怕什么都没选中）。
- `pixelSelection` 档无选区 → `'no-selection'`（不静默降级成「对整张画布跑一次」——那会改掉用户没框选的地方）。
- 未知 scope → `'bad-scope'`，**不静默按 any 跑**（类型闭合，发生了就是代码错，必须报出来）。
- 报告里的 `target`：逐层档 = `layer.name`；`any` = 当前层名；`pixelSelection` = `'选区'`（写层名会指错对象）。

**三条复用纪律**：图层遍历只有这三个公共件，A4 已把它们改名成 `mm_layer_walk` / `mm_layer_walkIndexOrder` / `mm_layer_selectedIndexes`。改名不是为了这轮方便：`mm_vec_exportLayer`（矢量化，`jsx/main.jsx:782`）**现在就在调** `mm_text_selectedIndexes`，`text_` 这个名字早就不准，只是没人改。下次谁再需要遍历就从这里拿，别写第四份。

### 2.3 历史组与选中还原

```js
// 外层（不进历史组的准备）
$.global.__mm_scriptJob = { code: code, targets: targets, scope: scope };
$.global.__mm_scriptReport = null;
doc.suspendHistory(label || '自定义 JSX', 'mm_script_doRun()');
var report = $.global.__mm_scriptReport || { total: 0, failed: [] };
$.global.__mm_scriptJob = null;
$.global.__mm_scriptReport = null;
return report;
```

- 参数走 `$.global`，因为 `suspendHistory` 第二个参数只能是脚本字符串（照 `mm_text_writeAll` 的写法）。
- **一次点击 = 一条历史**：所有目标一起进同一个撤销组，`Ctrl+Z` 一次全退。
- **`any` 档没有文档也要能跑**（`app.version`、`$.os` 这类脚本与文档无关）：无文档时不包历史组、直接执行一次，`layer` 为 `null`、`mmTargets` 为空数组。其余 5 档无文档一律 `'no-doc'`。
- **选中还原**：进循环前存 `doc.activeLayer`，循环结束 `doc.activeLayer = saved`；`any` / `pixelSelection` 档不切换，无需还原。还原失败**不吞**：`mm_log` 记一行再继续（脚本可能把原层删了，那是用户脚本的行为，不是我们的失败，但必须留痕）。
- 逐层循环内 `try { eval(code) } catch (e) { failed.push({ target: layer.name, reason: String(e.message || e), line: Number(e.line) || 0 }) }` —— 一层失败不中断，且**行号必须带上**（`ADR-0008`：`detail` 至少带行号之一，否则「第几行炸的」只能靠猜）。

### 2.4 能力表与解析器

```ts
// core/ps/capabilities.ts
scriptRun: {
  fn: 'mm_script_run', gate: 'core', channel: 'direct', timeout: WRITE_TIMEOUT,
  parse: scriptReportRaw
}
```

三条必须写清：

1. **不加 `require`**：`scope` 是运行期值，`spec.require` 拿不到参数；挂了 `requireTextLayer` 会把「不指定」档直接挡死。
2. **不用 `LONG_TIMEOUT`**：`capability.test` 断言「只有标 `longTask` 的才许用 300s，且全仓只有一个（`callAction`）」。用户脚本超 60s 报 `TIMEOUT`（队列放行，PS 可能还在跑）。要放宽必须先改那条守卫，单独一轮。
3. **解析器就近放** `core/ps/script-raw.ts`：`core/ps/script.ts` 要 import 能力表，解析器放一起就成运行时环（与 `text-batch-raw.ts` 同一理由）。

`scriptReportRaw(raw)`：

1. `unwrapRaw` 先折约定值（`no-doc` / `no-target` / `no-selection` / `bad-scope`）；
2. `parseJson` → 必须是对象；
3. `total` 是非负整数；`failed` 是数组，每项 `target` / `reason` 是非空字符串、`line` 是非负整数；
4. `result` 可缺省；存在时必须是字符串；
5. 任一条不满足 → `PS_BAD_PAYLOAD` + 原文前 120 字进 `detail`。

**能力表守卫**（`ADR-0004` 的级 3「测试扫描」；`ADR-0009` 只允许官方测试命令，单测在允许范围内）：`capability.test` 加一条断言 `CAP.scriptRun.require === undefined`。因为「不加 require」是个反向约束，光靠文档写着，下一个人想给用户脚本加个文字前置时会顺手加上——那条断言会当场红。

`raw.ts` 的 `RAW_FAILURES` 加三个：`'no-target'` / `'no-selection'` → `PS_WRONG_LAYER`（前提不满足，`MessageBar` 的 soft 码，走灰字）、`'bad-scope'` → `VALIDATION`。`no-doc` 已有；`error:` 由 `callJsx` 统一折 `PS_ERROR`（`bridge.ts:162`），这里不重复。

> 为什么「没有选区」用 `PS_WRONG_LAYER` 而不是新加一个码：`ErrorCode` 是闭合联合，加码要同步 `MSG.codeReason` 与 `MessageBar` 的 soft 清单（三处）。而 `PS_WRONG_LAYER` 在本仓的既定语义就是「前提不满足」（`layer.ts:107` 原话：数量不符不是故障，用 `PS_WRONG_LAYER` 让消息行走灰字）。理由写在这里，避免下一个人以为是笔误。

### 2.5 数据层原语

**`src/domain/script.ts`**（纯函数，零 IO，可单测）

```ts
/* 白名单不在这里：`SCRIPT_SCOPES` 在 `types/script.ts`，本文件只 import 它 */

/** 单条校验：只判结构，不判语义；认不出返回 fail（由 decodeList 决定整份失败还是跳过） */
export function scriptOf(value: unknown, path: string): Result<ScriptItem>;

/** 读视图：结构坏 reject，项坏 filter 并记账 */
export function decodeScripts(raw: unknown): Result<{
  items: ScriptItem[];
  records: unknown[];
  dropped: Dropped[];
}>;

/** 写路径：只要裸数组，坏项原样保留（不许拿 items 写回） */
export function decodeScriptRecords(raw: unknown): Result<unknown[]>;
```

单条校验（四项，全部结构判断）：`id` 非空串；`name` 非空串且长度 ≤ `SCRIPT_NAME_MAX`；`scope` 在 `SCRIPT_SCOPES` 里；`code` 非空串且长度 ≤ `SCRIPT_CODE_MAX`。

两个上限进 `src/config.ts`：`SCRIPT_NAME_MAX = 40`、`SCRIPT_CODE_MAX = 20000`（约 20 KB，防误粘整个文件把 `evalScript` 撑爆）。

**`src/repo/script-repo.ts`**（唯一读写入口；文件名常量只有这一处）

```ts
export const SCRIPT_FILE = 'custom-scripts.json';

export function readScripts(): Result<{ items: ScriptItem[]; dropped: Dropped[] }>; // 读视图
export function readScriptRaw(): Result<string>;                                    // 原文（云同步上传用，不 parse）
export function createScript(item: ScriptItem): Promise<Result<void>>;
export function updateScript(
  id: string,
  patch: Partial<Pick<ScriptItem, 'name' | 'scope' | 'code'>>
): Promise<Result<void>>;
export function removeScript(id: string): Promise<Result<void>>;
export function reorderScripts(from: number, to: number, position: DropPosition): Promise<Result<void>>;
export function replaceScriptsRaw(text: string): Promise<Result<void>>; // 云同步写回（原文）
```

- 全部走 `updateOrCreateJsonFile`：文件不存在 = 用户新增的第一条，走 create 分支、不产生 `.bak`；存在 = 读改写。写路径的 decoder 是 `decodeScriptRecords`（拿到的是**裸数组**），所以写回时坏项原样保留——**不拿 `items` 写回**（`filter` 跳过坏项，写回等于「读的时候跳过、写的时候删掉」，对用户手写的代码不可逆）。
- `readScripts` 的返回**不带 `records`**：写路径的读取发生在 `updateOrCreateJsonFile` 内部，命令层拿不到也不需要原始数组。多暴露一个字段就是多一个没人用的出口（`ADR-0002`）。
- `readScriptRaw` 与 `readScripts` 是两个读入口，但不是两条线：前者给云同步取**原文**（不 parse，避免洗掉未知键），后者给页面取**投影**。同 `repo/action-repo.readWarehouseText` 的先例，文件头写明各自消费者。
- `updateScript` **逐键赋值**，不写 `{ ...record, ...patch }`：`patch` 是 `Partial`，`{ name: undefined }` 会把名字覆盖成 `undefined`（`exactOptionalPropertyTypes` 是关的，编译不报），那是静默写坏数据。`if (patch.name !== undefined) next.name = patch.name;` 三行，未知键照样保留。
- `reorderScripts` 复用 `domain/reorder.applyListDrop`。

**`src/store/script.ts`**（只读投影，照 `store/text` 的单源形态）

interface ScriptState {

### 2.6 原语边界：与 `diag.runDebugScript` 的分工（`ADR-0005` 必须先答）

`ADR-0005` 只问一句：**加新入口前，旧的能不能同时删掉？**

答：**不能，而且不是「迁移成本高」，是能力差异**。`runDebugScript` 用 `evalScript` 直发代码，**不依赖 `jsx/main.jsx` 是否加载成功**；`runScript` 走 `mm_script_run`，jsx 没加载就没有这个函数。而「jsx 加载失败 / 某个函数不存在」正是调试页要诊断的场景——把调试入口改成依赖 jsx，等于把唯一的自诊断工具和它要诊断的对象绑在一起。

**为什么不加机器闸**（`ADR-0009`）：能想到的两种闸都是「反向闸」——① ESLint 限制 `core/ps/diag` 的 import 方，换个文件 import 就绕过去；② 自写扫描脚本判「谁调了 runDebugScript」，同样可绕，还要多维护一套解析器和豁免名单。按三级阶梯，这条只能落在**级 3（写清楚）**，并写明为什么升不到级 1/2：两个函数的差异是「依赖不依赖 jsx 加载」，TS 表达不了「这个模块在 jsx 坏掉时仍然可用」。

| | `diag.runDebugScript` | `core/ps/script.runScript` |
|---|---|---|
| 给谁 | `/debug` 页，排障 | `/script` 页，用户按钮 |
| 依赖 | **不依赖 jsx**（`evalScript` 直发） | 依赖 `mm_script_run` 已加载 |
| eval 在哪 | TS 侧拼 `eval` 发给 CEP | jsx 内逐个目标 `eval` |
| 返回 | 表达式回值 / 空串 | `{ total, failed, result? }` |
| 历史组 | 无 | 有（一条） |
| 作用范围 | 无 | 6 档 |

纪律（级 3，两个文件头互相指认 + `CONVENTIONS` §4.8 例外表登记）：

- 业务不许调 `runDebugScript`；调试页不许调 `runScript`。
- 迁移路径写死：若将来调试页不再需要「jsx 未加载也能跑」，**删 `runDebugScript` 改调 `runScript`**，不许并存。
- 唯一共享的是 `error:` 前缀拆分，已经在 `bridge.ts` 统一，**不抽第三个文件**。

> 曾考虑把 TS 侧 `eval` 包装抽成 `core/ps/eval-code.ts` 两边共用。结论是不抽：两处 eval 发生在不同侧（一个在 CEP 字符串里，一个在 jsx 里），硬合并只会多一层壳，且壳里没有真逻辑。

### 2.7 像素选区的归属（plan 18 §4.1 的条件已触发）

现状：`mm_ocr_selectionRect(doc)` 是 `jsx/main.jsx` 里的**私有 helper**，不在 `CORE_FUNCS`、不在能力表、TS 侧看不到（plan 18 §9 明确记录）。plan 18 §4.1 把「抽公共层的条件」写死为：**第二个功能也要读像素选区**。自定义 JSX 就是第二个，条件成立。

**只做一半，并说明为什么**：

| 计划 | 裁定 |
|---|---|
| jsx 侧抽公共件 | **做**：`mm_ocr_selectionRect` 改名 `mm_sel_bounds(doc)`，仍是同文件内的纯 helper，`mm_ocr_exportImage` / `mm_ocr_eraseOriginal` / `mm_script_run` 三处调它 |
| `core/ps/selection.ts` + 能力表行 `mm_sel_getBounds` | **不做**：本轮 TS 侧零消费者（script 的目标解析与 `mmSelection` 注入全在 jsx 内），建表行等于多一次 `evalScript` + 一个中间态（两次调用之间用户能改选区），正是 plan 18 §4.1 拒绝它的那条理由 |

命名按 plan 18 的要求与图层选择一眼可分：`mm_sel_*`（像素选区）vs `mm_layer_getSelection`（选中图层数），两者在能力表里相邻也不许混。

改名时顺手修一处兜底（`ADR-0008`）：现在 `mm_ocr_selectionRect` 的 `catch` 只 `return null`，「没有选区」与「读 bounds 时抛了别的错」同形。改成 `catch (e) { mm_log('mm_sel_bounds: ' + e.message); return null; }` —— 返回 `null` 不变（无选区是正常态，属 `ADR-0008` 的例外），但错误原因必须留痕。

文档同步：plan 18 §4.1 与 plan 20 §1 各加一行指针（「函数已改名 `mm_sel_bounds`，见 plan 22」），不留旧名。

## 3. 六个作用范围（点击时到底做什么）

| # | scope | 目标 | 执行次数 | 注入 |
|---|---|---|---|---|
| 1 | `any` | 无（`layer` = activeLayer，`mmTargets` = 选中集合） | 1 | `layer` 可能是任意层 |
| 2 | `layers` | 选中集合 | N | `layer` |
| 3 | `textLayers` | 选中 ∩ 文字层 | N | `layer` |
| 4 | `shapeLayers` | 选中 ∩ 形状层 | N | `layer` |
| 5 | `docTextLayers` | 全文档 ∩ 文字层 | N | `layer` |
| 6 | `pixelSelection` | 像素选区（不遍历） | 1 | `mmSelection` 必非 null |

- 2–5 要求至少 1 个目标层（否则 `no-target`）；6 要求有蚂蚁线（否则 `no-selection`）。
- 1 不判选中：一个「导出当前文档」的脚本不该因为没有选中而被挡。
- `mmTargets` / `mmSelection` **所有档都注入**，所以「对选中的每个图层、在选区内操作」这种组合不用单独开一档——脚本自己遍历 `mmTargets`、读 `mmSelection` 即可。
- 文字层口径：`docTextLayers` 走 `mm_layer_walk`（**是否含隐藏层由 A1 探针 2 确认**，确认前不许在界面上写「整个文档」）；`textLayers` 走选中集合。两处口径不同是既成事实，不在本轮统一。

## 6. 失败与边界

| 情形 | 处理 |
|---|---|
| 空 `code` / 超 `SCRIPT_CODE_MAX` | 前端 `VALIDATION`，不发 jsx |
| 2–6 档没有目标层 | jsx `'no-target'` → `PS_WRONG_LAYER`，消息行灰字「没有可执行的图层」 |
| `pixelSelection` 档没有蚂蚁线 | jsx `'no-selection'` → `PS_WRONG_LAYER`，灰字「请先框选一块区域」；**不降级成对整张画布跑一次** |
| 某层抛错 | 进 `failed`，其余层继续；报告里带层名与宿主原话 |
| 脚本 60s 未返回 | `TIMEOUT`（队列放行，PS 可能还在跑） |
| 脚本死循环 | **PS 卡死，面板停不下来**。硬限制，界面上必须写清，代码兜不住 |
| 锁定层 / 组 | 用户脚本自己会抛，进 `failed`；我们不加额外前置 |
| 撤销 | 一次点击一条历史，`Ctrl+Z` 一次全退 |
| 中文 / 引号 / 换行 / 反斜杠 | 穿「JSON 文件 → `JSON.stringify` → `toJsxArg` 单引号包裹 → jsx `eval`」四层，真机必验（§8 第 1 条） |
| 用户脚本调 `mm_*` | 允许，但**不承诺 API 稳定**；`mm_*` 是内部实现，改名/删除会让脚本坏。编辑器旁写一句 |
| 写坏文件 | 单文件全量重写，`.bak` 只留上一版；靠 `records` 保留坏项 + `useDraft` 不逐字写盘 |

- `domain/cloud.ts` 加 `SCRIPT_UNIT = 'script.custom'`（`units` 是自由 map，协议不改）。

## 8. 验收（真机）

1. 代码含中文 / 单双引号 / 换行 / 反斜杠 → 执行成功（四层转义一起验）。
2. 空选中点 `layers` → 灰字「没有可执行的图层」，一次 jsx 都不发。
3. 3 个选中层，脚本改 `layer.name` → 3 层都改；`Ctrl+Z` 一次全退。
4. 选中里 1 文字 + 2 普通，`textLayers` → 只改文字层。
5. `docTextLayers` → 全文档文字层都改（含隐藏层，确认口径）。
6. `any` + 什么都不选 → 仍然跑一次，`layer` 是当前 activeLayer。
7. 第 2 层脚本抛错 → 报告 `failed` 有层名与原话，第 3 层照跑。
8. 跑完 `activeLayer` 回到执行前那个。
9. `pixelSelection` + 框一块 → `mmSelection` 是 px 数字（不是 UnitValue），脚本 `app.activeDocument.selection.bounds` 与它一致。
10. `pixelSelection` + 无选区 → 灰字「请先框选」，不发 jsx 到执行阶段。
11. 选区拉到画布外 → `mmSelection` 被 clamp 在画布内，脚本拿到的宽高与可见区域一致。
12. 脚本 `while(true){}` → 60s 报 `TIMEOUT`，PS 仍卡（记录现象，不修）。
13. 云同步：上传 → 另一台下载 → 脚本在；伪造一份没有 `script.custom` 的老快照 → 下载成功且本地脚本不动。
14. OCR 两条（导出 / 抹除）在改名后行为不变。

## 9. 未验 / 风险

> 下面第 1 / 3 / 4 / 5 条由 §1.5 A1 的探针直接回答。**探针跑完把实测写在条目后面，不许留「未验」**——未验的假设写成结论，就是下一轮返工的起点。

1. **`eval` 在 `suspendHistory` 的字符串函数里能否看见 `$.global` 与局部 `layer`**：`mm_text_writeAll` 同构但从未真机验证过（`text-batch.ts` 文件头自己标着待核实）。这是阶段 1 第一件要验的事。
2. **逐层切 `activeLayer` 对组内子层是否可用**：可能要 `layer.selected = true` 或先展开组；`activeLayer = layer` 在组内层上失败的表现未验。
3. **选中组时 `targetLayers` 返回组还是子层**：影响 `layers` 档的语义（组算 1 个目标还是摊平）。v1 按「返回什么就执行什么」，不摊平。
4. **60s 是否够**：导出类脚本可能超；放宽要改 `capability.test` 的 `longTask` 守卫，属独立一轮。
5. **用户脚本依赖 `mm_*` 的版本漂移**：同步到旧扩展的机器会坏，只能靠文档与提示，无法技术上兜住。
6. **`mmSelection` 是执行前快照**：脚本内部自己改选区后它不会跟着变。这是有意的（避免每次 `eval` 重算），但必须写进注入变量表旁的说明，否则用户会以为它是实时的。
7. **选区与「复制文档」的关系**：`mm_ocr_exportImage` 是在副本上 `crop`，`mm_sel_bounds` 读的是**原文档**的选区（plan 18 注释：副本带自己的选区状态，早读少一个中间态）。`mm_script_run` 直接在原文档执行，不存在这个差异；改 `mm_sel_bounds` 时不要把这个前提写反。

| 空 / 超长 `code` | 1 | `scriptOf` 唯一判据（写入与解码调同一个函数） |
| 写路径保留坏项 | 2 抄不错 | `decodeScriptRecords` 是写路径唯一 decoder |
| 文件名 | 2 | `SCRIPT_FILE` 只在 `repo/script-repo` |
| 像素选区读取 | 2 | `mm_sel_bounds` 唯一实现，3 个消费者 |
| `scriptRun` 不加 `require` | 3 写清楚 | 文字 + `capability.test` 一条断言（官方测试命令内，不是自写扫描） |
| 与 `diag` 的边界 | 3 | 两个文件头 + `CONVENTIONS` §4.8（结构上升不上去，见 §2.6） |
| 用户脚本写作规范 | 3 | 独立文档；用户代码不受本仓类型约束 |

> `ADR-0009` 已于 2026-11-09 按本仓事实改写（示例换成 `tsc` / `eslint` / `vitest` / `core/http` 那套，TD-13-8 销账）；本条按它现行正文适用。另：`AGENTS` §3 现行口径是「禁止新增任何闸，除非用户许可；缺闸不算违规，不得因缺闸登记债」，所以本 plan 一条闸都不加。

### 12.3 这轮改掉的 5 处不自洽（写在这里，避免下一个人再提一遍）

1. 报告同时存 `ok` 与 `total` → 两个真相；删 `ok`，成功数派生。
2. `runScript` 再判一次空 `code` → 同一失败的第二个解释；删掉，判据只在 `scriptOf`。
3. `SCRIPT_SCOPES` 数组 + 手写联合类型 → 必然漂；改 `as const` 派生。
4. `updateScript` 盲 spread `patch` → `{ name: undefined }` 编译过、数据坏；改逐键赋值。
5. 给 `diag` 边界加 ESLint 闸 → 反向闸，换个文件就绕过；改级 3 文字。
