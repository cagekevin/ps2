# 21 · 一键抠图（常用页新增按钮，RMBG-1.4）

日期：2026-11-03
状态：**代码已落地（2026-11-16），真机待验**
目标：常用页多一个按钮，点一下把当前图层抠成透明背景的新图层。自己用，精度 1024 够，不起服务。

---

## 0. 六条裁定

1. **不起常驻服务，改成「每次点击 spawn 一个 Python 进程」**：跑完就退出，内存不累积。
2. **Python 里用 onnxruntime，不用 torch**：onnx 加载 0.3–0.5 秒，torch 光 `import` 就要 3–5 秒。这是「快不快」的关键，不是「Python 还是 WASM」。
3. **模型用 RMBG-1.4（ISNet，约 176MB onnx）**：够用、快、体积可接受；换 RMBG-2.0 只改脚本里的模型路径。
4. **模型放扩展目录之外，位置规则与 DLSS 引擎完全一致**：176MB 超 GitHub 单文件 100MB，也**不能**进 `public/`（会随每次部署拷进扩展目录、卸载即丢）。候选固定两条、顺序固定（`CONVENTIONS` §5.2）：**用户指定路径**（prefs `cut.model`，设置页选一次）→ **默认位置** `%APPDATA%\Maomao\assets\cut\model.onnx`（`npm run fetch:model` 下载）。两条都没有就报错并列出试过的绝对路径。
5. **原图层不动**：结果是新图层盖在原层上方，`Ctrl+Z` 一步撤掉。
6. **第二阶段再打包成 exe**：PyInstaller **`--onedir`**（不是 `--onefile`），模型**留在 exe 外面**。代码不变，只换 `config.ts` 的调用路径。本轮不做。

## 1. 为什么是 A′（七个方案对比）

| 方案 | 单张 | 内存 | 外部依赖 | 风险 | 结论 |
|---|---|---|---|---|---|
| WASM（onnxruntime-web） | 5–15 秒 | 峰值 1GB 级，**崩了是白屏** | 无 | wasm 路径解析未验 | 淘汰 |
| spawn Python + **torch** | 5–10 秒 | 进程退出释放 | Python + torch（~2GB） | 慢 | 淘汰 |
| **spawn Python + onnxruntime** | **2–3 秒** | **进程退出释放** | Python + onnxruntime（~200MB） | 无 ABI 问题 | **选它** |
| 常驻 Python 服务 | 1–2 秒 | 常驻 1–2GB | 同上 | 要开窗口不能关 | 违背约束 |
| onnxruntime-node | 1–2 秒 | 原生内存 | 无 | 平台/ABI，没 PS 测不了 | 备选 |
| PS 自带「移除背景」 | 1–2 秒 | 0 | 无 | 不能换模型 | 保底（可先对比） |
| 云端 API | 1–3 秒 | 0 | 联网 + 额度 | 图要上传 | 不做 |

**A′ 的代价只有一个**：每张多约 0.5 秒进程启动。换来的是「不会把面板吃崩」+「换模型改一行」。

**为什么比 WASM 强**：WASM 的线性内存 32 位上限 4GB，ISNet 在 1024 输入下中间特征图是 GB 级，增长失败直接崩面板；Python 进程的内存由系统管，跑完就还给系统。

## 2. 文件放哪（**脚本进 `public/`，模型进用户指定目录**）

| 文件 | 位置 | 来源 | 进 git |
|---|---|---|---|
| `cut.py`（推理脚本，约 60 行） | `public/vendor/cut/` | 我们写 | ✅ |
| `requirements.txt`（onnxruntime / numpy / Pillow） | `public/vendor/cut/` | 我们写 | ✅ |
| `model.onnx`（RMBG-1.4，约 176MB） | ① 用户指定（prefs `cut.model`）② 兜底 `%APPDATA%\Maomao\assets\cut\` | 用户自备，或 `npm run fetch:model` 下到兜底位置 | ❌ 不在仓里 |

- **脚本放 `public/`**：Vite 拷进 `dist/vendor/cut/`，扩展里一定有（同 `public/vendor/vtracer/`）；`tools/` 不部署。
- **模型两条候选、顺序固定**（`CONVENTIONS` §5.2）：先读 prefs `cut.model`（设置页「选择模型文件」写入的绝对路径），空或文件不存在再看 `%APPDATA%\Maomao\assets\cut\model.onnx`。只有放 `public/` 才会随每次部署拷进扩展目录、卸载即丢，也才会撞 GitHub 单文件 100MB；放这两处都不沾。兜底目录里附一份 `README.md` 说明装哪。
- **模型是文件不是目录**：`cut.model` 存 `.onnx` 的绝对路径，`existsSync` 判定即可（DLSS 是目录 + 目录内找 exe，两者形状不同但候选顺序同一条规则）。
- 部署：`deploy.mjs` 照旧只拷 `dist/`（`dist/vendor/cut/` 由 Vite 从 `public/` 拷进去），并在必需清单里校验 `dist/vendor/cut/cut.py` 存在；模型缺了运行时给明确提示（§6）。

### 2.1 第二阶段：打包成 exe 时的布局

| 形态 | exe | 模型 | 启动 | 换模型 |
|---|---|---|---|---|
| `--onefile` 全包 | ~300MB | 内含 | 2–4 秒（每次解压到 temp） | 重新打包 |
| **`--onedir` + 模型外置** | **~90–120MB** | 旁边 176MB 文件 | **<1 秒** | 换个文件即可 |

总占用都是 ~300MB（Python 运行时 ~20 + onnxruntime ~30–50 + numpy/Pillow ~40–60 + 模型 176 + 壳 ~10）。

选 `--onedir` 的两个理由：① onefile 每次启动要解压 300MB，把 A′ 省下的时间又还回去；② 模型外置后换 RMBG-2.0 不用重打包。exe 与 `cut.py` 同放 `public/vendor/cut/`（随 dist 部署），模型仍外置（候选见 §2）；插件侧只改 `config.CUT_PYTHON` 指向 exe。

**前处理 / 后处理三条硬规则（照鲜艺逆向结果，改任一条结果就废）**：

| 环节 | 唯一写法 | 改了会怎样 |
|---|---|---|
| 喂图 | `Image.resize((w, h), BILINEAR)` 直接 squash 到模型输入尺寸，**不 letterbox** | 灰底留边会被模型当背景，主体边缘糊出一圈灰 |
| 归一化 | `x/255 - 0.5`（等价 mean 0.5 / std 1.0） | 用 ImageNet 的 0.485/0.229 整张掩码系统性偏亮/偏暗 |
| 出 alpha | 先 `resize` 回原图尺寸，再 **min-max** 拉到 0–1 | 不做 min-max，玻璃/发丝的半透明边缘糊成一片灰 |

依据（2026-11-16 逆向 `鲜艺AI抠图.exe`）：`src\rmbg.rs` 里的错误串 `"Incorrect target image width"` / `"Somehow image was resized to incorrect size"` 说明它显式 resize 到 target 尺寸（squash）；常量池 `0x10f9cd0` 处连续 `255.0, 0.5, 1.0, 0.0` 四个 float32 说明归一化是 `x/255 - 0.5`；全 exe 扫不到 `0.485`/`0.229` 任一 ImageNet 参数。
复现验证：同一张 682×682 商品图，本脚本输出按 alpha bbox 裁切后 549×352，鲜艺输出 548×351；缩到同尺寸比 alpha，平均绝对差 **1.06/255**，**97.7% 像素差 ≤2**。

**第四条是我们加的，故意偏离鲜艺**（2026-11-17）：`cut.py` 的 `fill_enclosed` 把「被轮廓围住的内部」抬到 `SOLID_FLOOR = 0.35`。原因：模型只看 RGB，玻璃内部是「透过玻璃看到的背景」，颜色与背景一致 → 判成背景（alpha≈0），结果只剩一圈空壳（用户实测「像被挖空」）。行业做法是内部保留「两三成背景灰」（0.2–0.4），**不是填成 1.0**（那会变塑料）。所以上面那句「1.06/255」只对**不透明物体**成立；透明物体上我们与鲜艺不同，刻意如此。前提：轮廓闭合；敞口容器会从缺口漏进去，内部填不上（此时行为与改前一致）。

**为什么导出要第三个函数**：现有两个导出各有目的 —— OCR 的是 JPG（无 alpha、按选区裁切）、矢量的是白底 PNG（vtracer 把透明当黑）。抠图要**透明 + 原尺寸**，三者在 jsx 文件头列一张对照表，不合并。

## 6. 边界与失败

| 情形 | 处理 |
|---|---|
| 模型没下载 | `IO_ERROR` + 报出试过的**每一条绝对路径**（prefs `cut.model` 那条 + 兜底 `%APPDATA%\Maomao\assets\cut\model.onnx`），提示「设置页选一次模型文件，或跑 npm run fetch:model」；不降级到 PS 自带抠图（两套实现） |
| 找不到 python | `IO_ERROR` + `detail: spawn ENOENT`，提示改 `config.CUT_PYTHON` |
| 没装 onnxruntime / Pillow | 脚本 stderr 里有 `ModuleNotFoundError`，原样进 `detail`，前端提示「按 requirements.txt 装依赖」 |
| 推理超时 | `runProcess` 的 `timeoutMs` 由 engine 传 `CUT_TIMEOUT_MS`（120 秒）——通用原语不带域常量；超时 kill 并报 `TIMEOUT` |
| 当前图层是组 / 智能对象 / 文字 | 导出失败 → 提示「先栅格化或选中像素图层」，不自动栅格化 |
| 中文 / 空格路径 | 参数走数组传给 `runProcess`（范本内部不经 shell、数组 spawn），不需要引号；jsx 侧 `File`/`Folder` 吃中文没问题 |
| 撤销 | 一步：`Ctrl+Z` 撤掉刚放上去的结果层；原层像素从未被改 |
| 结果位置 | **对齐 PNG 画布左上角，不是内容框**：抠图结果四周有透明留边（682×682 画布内容框只有 549×352、偏移 (70,167)），按内容框对齐会把整张图推偏留边那么多。`mm_placePngIntoDoc` 先量画布内内容偏移 `frameOffsetX/Y`，再让内容框落到 `left + frameOffsetX` —— 等价于画布左上角落在原层 bounds 左上角。DLSS 结果满画布不透明，两个偏移恒为 0 |
| 结果层命名 | 取「原层名 + 抠图」，图层面板里一眼看出是抠出来的；重名由 PS 自动加序号 |
| 临时文件 | 目录归 **Node 侧** `core/temp.prepareTemp('maomao-cut')`（`os.tmpdir()/maomao-cut/<时间戳>`），jsx 只吃传进去的绝对路径、不自己拼 `Folder.temp`。成功/失败都 `cleanupTemp`，删不掉只 `log.warn` |

## 8. 未验 / 风险

1. **RMBG-1.4 的 onnx 权重从哪拿**：官方给的是 pytorch；onnx 版来自社区导出（HuggingFace 上有 `rmbg-1.4` onnx 仓库），**导出质量与输入规范（1024、mean 0.5 / std 1.0）要对一次**，落地第一步就验。
2. **python 命令名**：Windows 上 `python` 可能是商店别名或不存在，常见是 `py -3`；先写常量，跑不通就改。
3. **速度**：2–3 秒是估算（进程启动 + 176MB 加载 + 1024 推理），没实测。
4. **许可**：RMBG-1.4 非商用，自己用没问题；将来要分发必须换 BiRefNet（MIT）。
5. 图标未定。
6. **模型缺失的报错要带路径**：两条候选（prefs `cut.model` / `%APPDATA%\Maomao\assets\cut\model.onnx`）都试过就全部列出（与 `.bak` 的「错误提示必须带路径」同判），否则用户不知道该把模型放哪；`fetch:model` 写兜底目录时目录不存在要建。

## 9. 形状审计（先写死，落地时对照）

| 问 | 答 |
|---|---|
| 「导出图层为图」有几处？ | 3 处，目的不同：OCR 的 JPG / 矢量的白底 PNG / 抠图的透明 PNG（jsx 文件头列对照表）。**返回形状对齐 OCR 与矢量**：`{ path, exportWidth, exportHeight, bounds }`，DLSS 的 `mm_dlss_exportLayer` 返回 `{ left, top, width, height, layerName }`（整个画幅合并可见，没有 `path`），属既有偏差（`TD-01-34`），本轮不动 |
| 「结果贴回文档」有几处？ | **1 处：`mm_placePngIntoDoc`**。DLSS 导回（`mm_dlss_finishResult`）与抠图（`core/ps/cut.placePng`）都调它，jsx 侧不再有第二份。它的 `frameOffsetX/Y` 量测服务抠图（结果有透明留边），DLSS 满画布不透明时恒为 0 |
| 「临时目录」有几处？ | **1 处：`core/temp.prepareTemp`**（参数化域目录名），DLSS 与抠图都用它。jsx 侧 OCR / 矢量的 `Folder.temp.fsName + "/ps_ocr_engine"` 等硬编码是既有偏差（`TD-01-35`），本轮不动 |
| 「跑模型」有几处？ | 1 处：`core/cut/engine.ts`（第二阶段换 exe 只改这里 + 一个常量） |
| 「找模型路径」有几处？ | 1 处：`core/cut/engine.resolveModel`，与 `core/dlss/engine.resolveRuntime` 同一条规则（`CONVENTIONS` §5.2 两条候选），形状对齐：`ok`+`null` = 没有、`IO_ERROR` = 拿不到 |
| 「spawn 子进程」有几处？ | **全仓 1 处**：`core/cep/process.ts` 的 `runProcess`（`GOVERNANCE` §4.1 已登记范本，DLSS 阶段 1 已落地）。`core/cut/engine.ts` 只拼参数与判输出，不许自己 `execFile` / `spawn` |

## 10. 不做的

- 不做常驻服务、不做 Python 依赖以外的运行时。
- 本轮不打包 exe（第二阶段，代码不变只换路径）。
- 不做边缘精修 UI（羽化/收缩）——先用 PS 的「选择并遮住」补。
- 不把结果做成图层蒙版：本轮没做出来（「应用图像」到蒙版通道报常规 PS 错误，「复制粘贴」从未验证成功），见 §3。不是蒙版不行，是我没做通。
- 不做批量抠图。
- 不改官方 14 项种子、不写用户文件。
- 不做模型档位切换 UI（换模型 = 设置页「选择模型文件」选另一个 `.onnx`，不建模型列表、不存多套）。
