# 21 · 一键抠图（常用页新增按钮，RMBG-1.4）

日期：2026-11-03
状态：**规划中**
目标：常用页多一个按钮，点一下把当前图层抠成透明背景的新图层。自己用，精度 1024 够，不起服务。

---

## 0. 六条裁定

1. **不起常驻服务，改成「每次点击 spawn 一个 Python 进程」**：跑完就退出，内存不累积。
2. **Python 里用 onnxruntime，不用 torch**：onnx 加载 0.3–0.5 秒，torch 光 `import` 就要 3–5 秒。这是「快不快」的关键，不是「Python 还是 WASM」。
3. **模型用 RMBG-1.4（ISNet，约 176MB onnx）**：够用、快、体积可接受；换 RMBG-2.0 只改脚本里的模型路径。
4. **模型放扩展目录之外**：176MB 超 GitHub 单文件 100MB，也**不能**进 `public/`（会随每次部署拷进扩展目录、卸载即丢）。`npm run fetch:model` 下到 `%APPDATA%\Maomao\assets\cut\model.onnx`，约定见 `CONVENTIONS` §5.2。
5. **原图层不动**：结果是新图层盖在原层上方，`Ctrl+Z` 一步撤掉。
6. **第二阶段再打包成 exe**：PyInstaller **`--onedir`**（不是 `--onefile`），模型**留在 exe 外面**。代码不变，只换 `config.ts` 的调用路径。本轮不做。

## 1. 为什么是 A′（七个方案对比）

| 方案 | 单张 | 内存 | 外部依赖 | 风险 | 结论 |
|---|---|---|---|---|---|
| WASM（onnxruntime-web） | 5–15 秒 | 峰值 1GB 级，**崩了是白屏** | 无 | wasm 路径解析未验 | 淘汰 |
| spawn Python + **torch** | 5–10 秒 | 进程退出释放 | Python + torch（~2GB） | 慢 | 淘汰 |
| **spawn Python + onnxruntime** | **2–3 秒** | **进程退出释放** | Python + onnxruntime（~200MB） | 无 ABI 问题 | **选它** |
| 常驻 Python 服务 | 1–2 秒 | 常驻 1–2GB | 同上 | 要开窗口不能关 | 违背约束 |
| onnxruntime-node | 1–2 秒 | 原生内存 | 无 | 平台/ABI，没 PS 测不了 | 备选 |
| PS 自带「移除背景」 | 1–2 秒 | 0 | 无 | 不能换模型 | 保底（可先对比） |
| 云端 API | 1–3 秒 | 0 | 联网 + 额度 | 图要上传 | 不做 |

**A′ 的代价只有一个**：每张多约 0.5 秒进程启动。换来的是「不会把面板吃崩」+「换模型改一行」。

**为什么比 WASM 强**：WASM 的线性内存 32 位上限 4GB，ISNet 在 1024 输入下中间特征图是 GB 级，增长失败直接崩面板；Python 进程的内存由系统管，跑完就还给系统。

## 2. 文件放哪（**脚本进 `public/`，模型进用户数据目录**）

| 文件 | 位置 | 来源 | 进 git |
|---|---|---|---|
| `cut.py`（推理脚本，约 60 行） | `public/vendor/cut/` | 我们写 | ✅ |
| `requirements.txt`（onnxruntime / numpy / Pillow） | `public/vendor/cut/` | 我们写 | ✅ |
| `model.onnx`（RMBG-1.4，约 176MB） | `%APPDATA%\Maomao\assets\cut\` | `npm run fetch:model` 下载 | ❌ 不在仓里 |

- **脚本放 `public/`**：Vite 拷进 `dist/vendor/cut/`，扩展里一定有（同 `public/vendor/vtracer/`）；`tools/` 不部署。
- **模型放 `%APPDATA%\Maomao\assets\cut\`**（`CONVENTIONS` §5.2）：会随每次部署拷进扩展目录、卸载即丢，还超 GitHub 100MB。目录里附一份 `README.md` 说明装哪。
- 部署：`deploy.mjs` 照旧只拷 `dist/`；模型缺了运行时给明确提示（§6）。

### 2.1 第二阶段：打包成 exe 时的布局

| 形态 | exe | 模型 | 启动 | 换模型 |
|---|---|---|---|---|
| `--onefile` 全包 | ~300MB | 内含 | 2–4 秒（每次解压到 temp） | 重新打包 |
| **`--onedir` + 模型外置** | **~90–120MB** | 旁边 176MB 文件 | **<1 秒** | 换个文件即可 |

总占用都是 ~300MB（Python 运行时 ~20 + onnxruntime ~30–50 + numpy/Pillow ~40–60 + 模型 176 + 壳 ~10）。

选 `--onedir` 的两个理由：① onefile 每次启动要解压 300MB，把 A′ 省下的时间又还回去；② 模型外置后换 RMBG-2.0 不用重打包。exe 与 `cut.py` 同放 `public/vendor/cut/`（随 dist 部署），模型仍外置在 `%APPDATA%\Maomao\assets\cut\`；插件侧只改 `config.CUT_PYTHON` 指向 exe。

## 3. 数据流

```
常用页按钮
  → commands/cut.cutCurrentLayer()
  → core/ps/cut.exportLayer()          jsx: 当前图层 → 透明 PNG（原尺寸）→ { path, width, height }
  → core/cut/engine.runCut(in, out)    spawn: python cut.py <in> <out> <model>
                                       （脚本内部：缩到长边 1024 → onnx 推理 → mask 放大回原尺寸 → 写 RGBA PNG）
  → core/ps/cut.placePng(out)          jsx: 打开 PNG → 作为新图层放进原文档
  → 删两个临时文件（失败只 log.warn）
```

缩放、合成、alpha 全在 Python 里做 —— **前端不碰 canvas，`domain` 层本轮没有新增纯函数**（也就没有可单测的部分，见 §9）。

**为什么导出要第三个函数**：现有两个导出各有目的 —— OCR 的是 JPG（无 alpha、按选区裁切）、矢量的是白底 PNG（vtracer 把透明当黑）。抠图要**透明 + 原尺寸**，三者在 jsx 文件头列一张对照表，不合并。

## 6. 边界与失败

| 情形 | 处理 |
|---|---|
| 模型没下载 | `IO_ERROR` + 「先跑 npm run fetch:model」（落 `%APPDATA%\Maomao\assets\cut\`），不降级到 PS 自带抠图（两套实现） |
| 找不到 python | `IO_ERROR` + `detail: spawn ENOENT`，提示改 `config.CUT_PYTHON` |
| 没装 onnxruntime / Pillow | 脚本 stderr 里有 `ModuleNotFoundError`，原样进 `detail`，前端提示「按 requirements.txt 装依赖」 |
| 推理超时 | `execFile` 带 `timeout: CUT_TIMEOUT_MS`（120 秒），超时杀进程并报 `TIMEOUT` |
| 当前图层是组 / 智能对象 / 文字 | 导出失败 → 提示「先栅格化或选中像素图层」，不自动栅格化 |
| 中文 / 空格路径 | 参数走数组传给 `execFile`（不经 shell），不需要引号；jsx 侧 `File`/`Folder` 吃中文没问题 |
| 撤销 | 一步：新图层单独一层，`Ctrl+Z` 撤掉它；原层从未被改 |
| 临时文件 | 成功/失败都删，删不掉只 `log.warn` |

## 7. 验收

1. 商品图（白底、浅灰底各一张）→ 点按钮 → 生成透明新图层，边缘无明显白边。
2. 原图层内容与蒙版完全没变。
3. `Ctrl+Z` 一次撤掉结果层。
4. 没下载模型 / 没装 python 时点击 → 提示明确原因，不崩、不静默。
5. 连点 3 次：每次 2–3 秒，内存不持续上涨（任务管理器看 python 进程退出）。
6. `npm run check` 全绿。

## 8. 未验 / 风险

1. **RMBG-1.4 的 onnx 权重从哪拿**：官方给的是 pytorch；onnx 版来自社区导出（HuggingFace 上有 `rmbg-1.4` onnx 仓库），**导出质量与输入规范（1024、mean 0.5 / std 1.0）要对一次**，落地第一步就验。
2. **python 命令名**：Windows 上 `python` 可能是商店别名或不存在，常见是 `py -3`；先写常量，跑不通就改。
3. **速度**：2–3 秒是估算（进程启动 + 176MB 加载 + 1024 推理），没实测。
4. **许可**：RMBG-1.4 非商用，自己用没问题；将来要分发必须换 BiRefNet（MIT）。
5. 图标未定。
6. **`fetch:model` 写到 `%APPDATA%\Maomao\assets\cut\`**：目录不存在要建；写失败必须报绝对路径（与 `.bak` 的「错误提示必须带路径」同判），否则用户不知道该把模型放哪。

## 9. 形状审计（先写死，落地时对照）

| 问 | 答 |
|---|---|
| 「导出图层为图」有几处？ | 3 处，目的不同：OCR 的 JPG / 矢量的白底 PNG / 抠图的透明 PNG（jsx 文件头列对照表） |
| 「放图片进文档」有几处？ | 1 处：`mm_cut_placePng`（vendor 的 `cy_insertionImage` 是「匹配到背景框」，不是这个用途） |
| 「跑模型」有几处？ | 1 处：`core/cut/engine.ts`（第二阶段换 exe 只改这里 + 一个常量） |
| 「spawn 子进程」有几处？ | 1 处（同上）。全仓此前没有 `child_process`，这是第一个，需在 `core/cep/node.ts` 旁注明 |
| 「常用页按钮」有几处？ | 官方 14 项仍只来自文件；本地按钮 1 处（视图层追加，不写文件、不参与拖拽/右键菜单） |
| 单测 | **本轮没有可测的纯逻辑**（缩放/合成都在 Python）；`npm run check` 只保证没踩坏别的 |

## 10. 不做的

- 不做常驻服务、不做 Python 依赖以外的运行时。
- 本轮不打包 exe（第二阶段，代码不变只换路径）。
- 不做蒙版精修 UI（边缘羽化/收缩）——先用 PS 的「选择并遮住」补。
- 不做批量抠图。
- 不改官方 14 项种子、不写用户文件。
- 不做多模型切换 UI（换模型改脚本一行）。
