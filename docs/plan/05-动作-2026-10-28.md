### 0.4 清单被证伪的 3 处

1. **仓库下拉项高度**：清单 §7.1 写 `28px`、§九 对照表写 `22px`。**CSS 实测 28**，以 28 为准。
2. **空组文案**：清单 §五 说「该分组没有动作」不属于 Action——半对。Action 自己的空态是
   **`该动作组空空如也`**（`:1795562`）；`addContext` 弹窗里另有 `*该分组没有动作`。两条都要收，别混用。
3. **删光分组的补名**：官方 `deleteGroup` 用 `this.text + "默认分组"`，而 `text` 在动作库的 List 上从未赋值
   ⇒ 真机很可能出现 `undefined默认分组`。**我们补「默认分组」**（§4.5 A-2）。
4. **底部竖线没有 `opacity: 0`**：清单 §九 把三个 scope 的 `.verline` 混成一条。
   动作页实测 `.verline[data-v-7b3c2fb6]{width:1px;height:13px;border:none;background-color:#333}`，
   **可见、13 高、#333**；`opacity:0` 属 `17d9aabc`（别的页）。
5. **仓库下拉里的「创建新分组」其实新建的是「仓库」**：`f_add` → `emit('add',1)` → `addWarehouseGroup()` →
   `wh.add()` → 往**仓库索引** `info.list` 里 push `{name:"未命名分组", fileName}`。
   名字叫分组、行为是仓库，是本页最容易搞混的一处，两个「新建」必须分开命名（§5）。

### 1.3 判定口径

- **动作库 = 索引文件 + 若干仓库文件**，一个库两个形状，别混。

- 「添加」有两个入口：**从 PS 添加**（`dz_getActionList`）与 **新建分组**（`addGroup`），别混。

## 3. 底层设计

### 3.1 `core/ps/action.ts`

| 函数 | jsx | 通道 | 参数 | 语义 |
|---|---|---|---|---|
| `callAction(item)` | `dz_callAction` | **调度**（`channel: 'dispatch'`） | `[{ group, name, alias? }]` 整个 item | 执行 PS 动作 |
| `getActionList()` | `dz_getActionList` | **直调**（`channel: 'direct'`） | 无参 | 取 PS 动作面板的分组与动作 |

- `callAction` 必须传**整个 item**（`:1823179` 已核）；缺 `group` 会执行到别的组。
- `getActionList` 返回**不解码**（可能有裸值），交给 `domain` 归一；形状 UNVERIFIED。
- **改判（2026-10-29，用户决定）**：`05` 原要求「先真机探针、确认存在再登记」。由于当前没有真机，用户指示**照抄可运行的 Vue 版实践**（`ps/src/cep/jsx/action.ts` 用同名函数、同样参数形状、`callAction` 给长超时）。于是两条 jsx 已直接登记进 `capabilities.ts` + `VENDOR_FUNCS`，`core/ps/action.ts` 已建；探针（`mm_diag_vendor` 的两个 `typeof`）保留，真机时用来复核。**风险**：我们这份 `vendor.jsx` 副本若缺这两个函数，仅动作页失效（探测分级后报 `PS_UNREADY` + `detail: fn:dz_callAction`），不再整片不可用。

- **前置核对（M0 第一件事）**：我们的 `jsx/vendor.jsx` 是 jsxbin（`@JSXBIN@ES@2.0`），**grep 不到函数名**，
  所以「`dz_callAction` / `dz_getActionList` 在不在这份副本里」**无法静态确认**。
  做法：先给 `mm_diag_vendor` 加两个 `typeof` 探测，真机确认存在**再**写进 `VENDOR_FUNCS`——

**校验策略**（与官方相反，见 §7.3）：

- **结构**坏（顶层不是数组 / 组不是对象 / `list` 不是数组）→ `CORRUPT`，**不回落默认、不自动修复**。
- **项**坏（动作缺 `group` / `name`）→ **跳过并记 `dropped`**（`path` 指到 `root[i].list[j]`），页面显示「N 项无法识别，已跳过」；
  写回时读**原始记录**，坏项原样留在文件里，只有用户显式删除才消失。
  「不静默丢」指的是**写回不许删**，不是「读的时候整份拒绝」——那会让一项坏导致整页不可用（`03` 真机踩过）。
- `alias` 为空串 = 无别名（官方会显示空标签，不照抄）。

**两处形状只在一处映射**：`dz_getActionList` 的 `[{ name, children: [{ name }] }]`
→ `[{ group, name }]`，只在 `domain` 里换，页面不许再换一次。

### 3.3 `domain/action-dzx.ts`

```ts
export interface DzxPayload { arrFileData: { name: string; data: string }[]; store: WarehouseIndex }
export function encodeDzx(index, files: { name: string; base64: string }[]): DzxPayload;
export function decodeDzx(raw: unknown): Result<DzxPayload>;

  nextIndex: WarehouseIndex;
```

- 外层字段名**照抄** `arrFileData` / `store`（`:301018`）：`.dzx` 是可导出的文件，改名后别的工具读不出；
  名字照抄，但校验不能松：
  1. `decodeDzx` 严格校验（`arrFileData` 是数组、每项 `name`/`data` 都是字符串、`store` 走 `decodeIndex`），
     不合格 `CORRUPT`，**绝不半信半疑地导**；
  2. 读写只走 `core/storage.readTextAt` / `writeTextAtAtomic`（`CONVENTIONS` §5 用户选路径例外），写前 `.bak`；
  3. `store` 先过 `decodeIndex` 再落，**不许把外部对象直接当 live 索引覆盖内存**。
- `planImportFiles` 是纯函数，只算「写哪些文件、索引变成什么」；**顺序在 repo**：
  **先写文件、最后写索引**（索引是入口，不能先指向还不存在的文件）。
  **不删旧文件、不回滚**：写失败就停在那份文件上返回 `IO_ERROR` 并带文件名；
  `.bak` 可恢复单份文件，索引没动所以库仍是导入前那一份。
- 追加模式文件名冲突 → 生成新 `fileName`；`name` 保持用户原样（官方也只在文件名上去重）。

### 3.7 数据流

```
页面 → commands/action → repo/action-repo → repo/json-file → core/storage
                     ↘ core/ps/action（执行动作 / 取 PS 列表）
store/action ← repo（只读投影）
```

三条硬规则：

1. **切仓库**：先 `updateIndex` 改 `index` → 再 `readLibrary`；反了会读到上一个仓库。
2. **索引与仓库不同步**（用户手改过）：读前校验越界 → **本次展示按 0 处理 + `log.warn`，不写盘**
   （读操作不许改用户文件）；等下一次真正的写操作再以 0 为基准落盘。
3. **导入不是事务**：先写文件、最后写索引。索引没写就等于没导入（库还是原来那份），
   残留的孤儿文件不可见也不影响读取，不为此写回滚。

### 3.9 与自由面板的协作（v1 只冻结契约）

动作页是自由面板的**数据来源之一**（和常用页、字体面板一样），两个入口：

| 入口 | 原版 | 我们要产出的 `FreePanelItemInput` |
|---|---|---|
| Ctrl+点击一个动作 | `$freePanelBox.show(name, "dz_useAction", item)` | `{ text: alias ?? name, key: 'dz_useAction', option: { group, name, alias? } }` |
| Ctrl+点击分组 | `$freePanelBox.batchShow("批量添加动作组", { text: [...], key: [...] })` | 同形状的 **N 条**，`key` 都是 `dz_useAction`；两个平行数组由执行器自己拼 |

**为什么现在定**：本仓已有 `domain/free-panel.ts`（文件形状 + `FreePanelItemInput`）与
`domain/free-panel-legacy.ts`（旧 key → 命令的唯一映射表）。自由面板落地时执行器按 `key` 查表调命令，
`option` 直接当 payload。**动作这条是最好的情况：`option` 就是 `call` 的参数，零翻译**
（字体面板那边还要 `fields` / `rename`）。所以这里只把 key 与 option 定死：

- `key = 'dz_useAction'`（key 是自由面板文件里唯一的执行约定，照抄原版）
- `option = { group, name, alias? }`（**整个动作项**，与 `dz_callAction` 入参同形）
- 执行器映射（未来加，本页不做）：`dz_useAction` → `commands.call(option)`

**v1 行为**：Ctrl+点击只 `toast.info('自由面板未上线')`，与 `useFontPanel.onCtrlClick` **同一句文案**，
不写 `sj_appFreePanel.json`（写错就是改用户文件格式）。分组批量同理，一个提示搞定，不做半成品。

**不把 `dz_useAction` 登记进 `VENDOR_FUNCS`**：它是官方前端的派发 key，最终执行 `dz_callAction`（§0.2）。

|---|---|
| `NOT_FOUND` | 自带预设 `.dzx` 不存在；**索引/仓库文件不存在不算**（按默认值读，不报错） |
| `CORRUPT` | 索引或仓库文件**结构**不符（顶层不是数组 / 组不是对象 / `list` 不是数组）；`.dzx` 解不出；PS 动作列表解析不出。**单个动作缺 `group`/`name` 不算 `CORRUPT`**，走 `dropped` 记账 |
| `IO_ERROR` | 写文件 / 删文件 / 选路径失败 |
| `VALIDATION` | 下标越界（写路径）；`deleteWarehouse` 只剩一个；别名校验 |
| `PS_UNREADY` / `PS_REJECTED` / `PS_ERROR` | 沿用 `core/ps` 的既有语义（`-1` → `PS_REJECTED`） |

#### D. 谁重读、谁不重读

- **数据类**（写索引或仓库文件）→ 成功后一律 `store.load()`，页面不自己拼状态。
- **参数类**（`setListColumns`）→ 只改 prefs + `set` 本地，**不读文件**。
- **执行类**（`call`）→ 不重读任何东西（改的是 PS 画面，不是库）。
- 页面**不做乐观更新**：拖拽结束只发命令，UI 等 store 重读后自然刷新。

#### E. 未定项（`UNVERIFIED`，M0 探针或首次真机确认）

## 8. 风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 文件被别的程序改过 | 我们读到的是改后的内容 | 不做并发保护（不存在两边同时写）；`repo/json-file` 写前 `.bak` 就够 |

| 大库卡顿（100+ 动作） | 渲染慢 | 分组本身是折叠的；只在展开的组渲染按钮；不做虚拟列表（v1 先量真机） |

## 9. 已定决策（不再询问）

1. 数据根用 `legacy`（`%APPDATA%\SheJiZhuLi`），不新开目录。
2. 坏文件 `CORRUPT`、不自动修复、不回落默认（官方 `checkError` 的行为不照抄）。
3. 勾选 12×12，不跟官方的 16。

5. 预设 `.dzx` 放扩展目录 `preset/`。
6. 分组行用公共件 `components/GroupHead`（与样式页同一实现；不再新建本页自有组件）。
7. 列数菜单用 `ContextMenu` 组合，不新建组件。
8. Ctrl+点击 v1 **只提示不写文件**，契约冻结（§3.9）；自由面板落地后由执行器按 key 查表，动作页不改。
9. 别名空串 = 无别名。
10. 删光分组补「默认分组」。
11. 页面零底层：`features/action` 不碰 jsx / 文件 / `JSON.parse`。
