## 一、为什么会出现两套读 JSON

不是命名撞车，是**两个时代、两种语义**：

| | `core/storage.readJson` | `repo/json-file.readJsonFile` |
|---|---|---|
| 出生 | 早期，给 `core/prefs` 用 | 样式库重构时抽出来 |
| 返回 | `T`，找不到/解析失败都返回 fallback | `Result<T>`，失败带码 |
| 判据 | 「偏好读不到就用默认值」 | 「文件三态由码承载」 |
| 额外职责 | 无 | 借 `repo` 层做结构解码、写队列 |

两边单看都合理，所以没被 grep 抓出来——重复的是**语义**，不是代码文本。防法只有一条：`CONVENTIONS` §0.5 的「唯一入口」表里写清「读 JSON 只能走 `readJsonFile`；要 fallback 在调用方做」，`prefs` 已经按这条改完。

## 三、顺带修掉的 bug

`recycleOldFiles` 覆盖导入前回收旧文件时，用 `readFileSync(..., 'utf8')` / `writeFileSync(..., 'utf8')` 复制 `kuStyle/*`、`Gradient/*` 的 PNG/PSD——**按文本读写二进制，图片会被写坏**。

改成 `core/storage.copyFileAt`（`fs.copyFileSync`），先复制成功再删原件；失败保留原件。这个 bug 藏在「自己写一套 fs」里，正是重复实现掩盖问题的典型。

## 四、剩下的「重复」是例外，不是债

| 项 | 为什么留 |
|---|---|
| `core/logger` 直接 `fs` | 日志不能反过来依赖 storage（会递归/丢日志） |
| 测试里直接 `fs` | `style-library.real.test` 读真实数据，属测试夹具 |
| `ContextMenu` vs `TagContextMenu` | 定位、关闭都复用同一 hook，只有视觉不同（蓝底 105px vs 深色菜单） |
| `core/storage.filePath` vs `core/paths.userSubPath` | 前者拼「根 + 文件名」，后者拼「用户目录绝对路径」；合并会引入循环依赖 |

## 六、结论

- 「两套读 JSON」不是孤例；这次按「队列 / 文件正文 / base64 / 字段校验 / 数组守卫 / 路径拼接」六个维度扫，全部收敛。
- 仍有大量**结构相似但语义不同**的代码（各 repo 的读函数、各 UI 浮层），不强行合并——合并的前提是同一能力，而不是长得像。
