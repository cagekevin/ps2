## 1. 总体结论

**收口完成，但有 3 处需要当场修的文档/样式漂移（已修）。**

这轮真正的价值不在视觉，而在删掉了两类「看起来能用、实际会静默出错」的结构：

| 删掉的 | 为什么必须删 |
|---|---|
| `--floating-width` 中间变量 | 变量没设上时 `width` 退回 `auto`（内容宽），下拉窄一截且从样式里看不出来 |
| `SelectBox` 的 `inset` 变体 | 同一个下拉在不同页面宽窄不同，是「两个下拉长得不一样」的来源 |
| 各下拉自写的 `position: fixed` + 描边 + 底色 + 阴影 | 5 份壳，改一次漏四处 |
| `.mm-font__list` 的 `display: grid` | 隐式行被 `stretch` 拉伸：筛选后项少 → 每行拉长（空白）+ `scrollHeight == clientHeight`（滚不动） |
| `.mm-font__item` 的 `content-visibility` + `contain-intrinsic-size` | 按估算高度占位，与真实内容不符时出现空白 |
| `FontPanelPage` 的属性区 `StateMask` | 「需不需要文字图层」用户自己看得见，遮罩是替用户做判断 |

## 6. 过程的教训（写给人看，不是给机器）

这轮在「下拉偏了」上浪费了 3 个来回，全部花在怀疑「是不是没部署 / CEP 缓存」，而真正的两个根因都在渲染链上：

1. `computeFloatingPosition` 在 `flip: false` 时仍按 `padding` 夹取——通栏触发器右边缘贴视口，夹取必然把面板往左推；
2. `.mm-font__list` 用 `display: grid` 做滚动容器，隐式行被 `stretch` 拉伸。

**规则**：用户报「空白 / 滚不动 / 位置偏」时，先看容器的 `display` / `align-*` / `overflow` / `contain-*` 与定位函数的 `clamp`，不要先假设构建或缓存。构建产物可用 `Get-ChildItem dist/assets | LastWriteTime` 一次证伪，不该反复要求用户“重开面板”。
