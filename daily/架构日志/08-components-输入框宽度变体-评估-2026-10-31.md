## 表 A：形状清单（「输入框宽度」这一个概念，现在有 3 个出处）

| # | 出处 | 判别位 | 是否生效 | 生产/声明点 | 消费点 |
|---|---|---|---|---|---|
| A1 | `variant: 'wide' \| 'half' \| 'fill'` | `.mm-text-field--${variant}` 类名 | **只 `fill` 生效**；`wide` / `half` 无 CSS 规则 | `src/components/TextField/index.tsx:33,67` | 12（`fill` 8 / `half` 3 / `wide` 1） |
| A2 | `--mm-input-w-wide: 80px` | 无（变量） | **零消费** | `src/styles/tokens.css:175` | `grep -rn "var(--mm-input-w-wide)" src` = **0** |
| A3 | 所在容器（`.mm-u-row` / `.mm-common__form-row` 的 1fr） | flex / grid | 生效，但**值不在 tokens**（`<input>` 浏览器默认宽 ≈ 20 字符） | `ui.css:87` 的 `.mm-input` **无 width** | 全部 12 |

**这是本缺陷的核心**：三处都在回答「输入框多宽」，其中 A1 的两个值取不到任何效果、A2 没有任何消费者、A3 的具体宽度由**浏览器默认值**决定 —— 视觉值落到了唯一允许写值的地方（`tokens.css`）之外，且 lint / stylelint **抓不到**（没有规则引用它，等于没有可校验的对象）。

## 表 B：入口清单

| 入口 | 谁在用 | 有无守卫 | 能否绕过判据 |
|---|---|---|---|
| `TextField.variant` | 12 个调用点全传 | 类型闭合（写错档位编译失败） | **能**：传的档位可以不存在实现 ⇒ 编译通过、视觉无效果 |
| 容器宽度（`flex` / grid） | 全部 | 无 | 本来就不该有守卫（布局归容器） |
| 页面局部覆盖宽度（`STYLE.md` §6.1 明文允许） | 0 处 | — | 合法通道，**应当**是定宽的唯一落点 |

**层数 = 1、形状数 = 3、入口数 = 2** ⇒ 三数对不上，兼职点 = `TextField`（兼了布局决策）。

## 表 C：判别语法

| 语法 | 数量 | 结论 |
|---|---|---|
| `variant="…"`（TextField） | 12 | 3 值里 1 值有实现 ⇒ 不是「档位」，是「一个开关 + 两个注释性取值」 |
| `variant="…"`（Button） | 10（`ghost` 5 / `primary` 5） | **对照组**：`ui.css:38-65` 有 `ghost` / `primary` / `danger` 三条规则 ⇒ 有实现的闭合联合，是合格范本 |

同一概念（「档位」）在一个组件里真、在另一个组件里假 —— 这是下一个人最容易照抄错的地方：照 `Button` 的写法给 `TextField` 加档位，会以为「加一个值就自动有样式」。

## 缺陷定性（四条判据逐条）

1. **层数 = 形状数 = 入口数**：1 / 3 / 2 ⇒ 不成立，兼职点见上。
2. **失败在类型上取不到值**：本形状不是失败臂，不适用；但有一个同构问题 —— **取了值也拿不到效果**（`wide` / `half`），比失败臂更隐蔽：失败臂至少 `status` 一判就知道，档位要打开 css 才知道它是空的。
3. **一个函数只干一件事**：`TextField` 同时干「渲染输入框」与「决定宽度档位」两件事 ⇒ 必拆（宽度归容器）。
4. **合法不是理由**：`variant="half"` 与不写宽度**都能跑、都过测**，但「宽度」这个概念现在能写出三种样子 ⇒ 债。

**半收口形态（`ADR-0001` 五类之一）**：一条未裁定的视觉决策（定宽 vs 自适应）已经被代码**单方面投了票**（实现只剩 `fill`），而类型、注释、文档、token 四处仍按「三档定宽」陈述。谁都能被下一个读者当权威抄一种。

## 原版证据（决定方向的关键，不是判断）

原版 Vue 的输入框**没有「三档语义」这个概念**，是**按位置给类**：

| 原版类 | 出现处 | 用法 |
|---|---|---|
| `inputcom1 mr5` | 常用页「放大 / 缩小」 | `baseInput` + `leftPadding: 6px` |
| `inputcom-2 mr0` | 复制数量 / 缩放比例 / 左右上下距离 | `baseIconInput` + `dark: true` |
| `inputcom-1` | 重命名图层、每行数量 | `baseInput`，宽度由类给（`docs/原版/app.v4.js`，CSS 未入仓） |

⇒ 我方把「每个位置一个宽度类」抽象成「三档语义 `variant`」是**自造的抽象**，且只实现了一档。按奥卡姆（`CONVENTIONS` §3.5「如无必要，勿增实体」）**删（方向甲）比补（方向乙）更省事**；要还原某个位置的定宽，`STYLE.md` §6.1 已明文允许页面**覆盖宽度**，不需要公共件出一个档位。

## 两条收口方向（取舍已列，等裁定）

| | 甲：宽由容器给（推荐） | 乙：恢复三档定宽 |
|---|---|---|
| 动作 | 删 `variant` prop；`.mm-text-field--fill` 并入基类（`flex:1 1 auto; min-width:0`）；删 `--mm-input-w-wide`；12 处删 prop；清 6 处过期陈述 | 补 `.mm-text-field--wide{width:var(--mm-input-w-wide)}` / `--half{...}`；token 复活；调用点不动 |
| N→1 | 宽度出处 **3 → 1**（容器）；档位 **3 → 0** | 宽度出处 **3 → 2**（prop 与容器仍能同时生效）；档位 **3 → 1** |
| 一档（写不出来） | **是**：删 prop 后传 `variant` 编译不过 | **否**：档位与容器宽度可以互相覆盖，两种写法都编译得过（只到二档） |
| 风险 | 4 处布局变化（`ExportPanel` 品质框 `wide` 1 + 导出宽高 `half` 2、`CustomTransformPanel` `half` 1），需真机看一次 | 视觉零风险，但把「自造抽象」固化 |
| 与仓内现状 | 8/12 已是 `fill`（等于已选甲） | 与 8/12 现状相反，要把 8 处 `fill` 改成具体档位 |
| 结论 | **推荐** | 只在「必须逐像素贴原版某个位置」时，对**那一处**用页面局部宽度覆盖，不复活公共档位 |
