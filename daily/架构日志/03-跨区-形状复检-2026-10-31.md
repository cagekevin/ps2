## 复检抓到的**两个新问题**（第一遍没看见）

### 新发现 A：`store/style-library` 存**整条 `Result`**（刀 2 的裸形状）

```
src/store/style-library.ts:44  indexResult: Result<StyleWarehouseIndex> | null;
src/store/style-library.ts:49  results: Record<KuKind, Result<KuGroup[]> | null>;
```

这正好是 `store/text` / `store/action` 文件头明确禁止的形态：
「存整条 `Result` 会让『ok』与『没读过』在这个字段上同形，读之前还要再判一次 `status`」。
⇒ store 层失败臂现在是**两种形状**：`Failure | null`（text / rename / action.reasons / common-use.reasons / font.XxxRead）
与 `Result | null`（style-library）。
**当日已修**（`TD-05-1` 已解决并归档）：`indexResult` → `indexFailure`、`results` → `failures`，
类型从 `Result | null` 收到 `Failure | null`（失败臂原样存 `code`/`reason`/`detail`），
值只在成功时落到 `libraries`；`StylePage` 三处读点改写（「读到但是空」的判据从 `result?.status === 'ok'`
改成 `groups !== null && !failure`），`dev/preview` mock 同步；新增 2 条形状凭据。
**为什么可以当轮修**：它只动一个 store 的三个读点，`typecheck` 全列出来，且不改渲染结构与样式——
与「要真机」的样式视觉改动不同类。

### 新发现 B：多源失败臂有**两种形态**

- 容器：`reasons: { index, library }`（action）、`reasons: { tiles, options }`（common-use）
- 平铺：`tagsRead` / `starsRead` / `classificationRead`（font，三个字段）

两者回答同一个问题（「这几个来源各自读到没有」），只是摆法不同。第三遍写的人可以任选一种 ⇒ 两种写法可抄。
**已裁定并当日修完**（`TD-05-2` 已解决并归档）：

- **目标形态**：单源 `failure: Failure | null`、多源 `failures: { <来源>: Failure | null }`；`Result` 不进 store。
- **裁定依据三条**：①多数派（`action` / `common-use` / `style-library` 已是容器，只有 `font` 平铺）；
  ②容器键与 store 里对应的值字段（`tickets`→`tiles`、`libraries`、`tags`）一一镜像，平铺要另记 N 个名字；
  ③单数 / 复数成对（`failure` / `failures`）比 `reasons` / `XxxRead` 好猜。
- **落地**：`reasons` → `failures`（2 个 store）；`tagsRead` / `starsRead` / `classificationRead` → `failures.{tags,stars,classification}`，
  且前两个原存整条 `Result`（页面为拿 `value.dropped` 只好再判 `status`）→ 现在只存失败臂，
  坏项记账按「属于值不属于失败」搬到 `dropped.{tags,stars}`；`reasonOf` 从「同时收 `Result` 与 `Failure`」收成只收 `Failure`。
- **纠正我上一节的说法**：`TD-09-4` 收的是「别用 `classificationDegraded: string`」，与「装表还是平铺」无关，
  所以这次迁移**不与那次结论冲突**（我当时写「会打架」是错的）。

> 这一条也修正我第一遍的说法：当时我把 `classificationRead` 写成「与单源 `reason` 是同一概念的第 3 个名字」，
> 更准确的说法是**多源容器 vs 平源平铺**两种摆法，与「单源字段叫什么」是两件事。
