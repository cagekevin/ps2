# 01 跨区 · 解析器失败语义（2026-10-30）

> 范围：`src/core/ps/raw.ts` + `src/core/ps/capabilities.ts` 的 `parse` 分配。
> 起因：应用字体时字体已换好，toast 报「文件无法识别」——查下去发现是解析器在**猜**，不是宿主在失败。

## 一、本次已修（不再是债）

| 项 | 现象 | 处置 |
|---|---|---|
| `strictVoid` 认不出 `{"code":"OK"}` | `ztgl_setFont` 换好字体后回这句，`errOf` 找不到 `err` → `CORRUPT` | `strictVoid` 整个删除，`setFont` / `applyFont` 改用 `lenientVoid` |
| `parseDataEnvelope` 不看 `err` | `{err:1}` 也把载荷交出去 = 假成功 | 补 `err !== 0` 判失败 |
| `lenientVoid` 认不出当成功 | 宿主真失败时界面照样提示成功，后续无从排查 | 只认有真机依据的成功写法（空串 / `undefined` / `null` / `0` / `1` / `{"code":"OK"}` / `{"err":0}`），其余报 `PS_ERROR` + `MSG.badPayload` + 原文进 `detail` |

## 二、探债（本轮未修，已登记）

### TD-01-18 「认不出」有 4 处构造、2 个码、3 种文案

`raw.ts` 13 个 `failWithDetail`，按语义归类后「宿主返回认不出」落在 4 处：

| 处 | 行 | 码 | 文案 |
|---|---|---|---|
| `parseJsxRaw` | 58 | `PS_ERROR` | `MSG.codeReason.PS_ERROR`（「PS 执行失败」） |
| `errOf` | 147 | `CORRUPT` | `MSG.codeReason.CORRUPT`（「文件无法识别」） |
| `lenientVoid` | 226 / 237 | `PS_ERROR` | `MSG.badPayload`（「返回数据无法识别」） |
| `strictPayload` 兜底 | 284 | `PS_ERROR` | `opts.whenFailed`（各能力自带） |

同一件事四种说法 ⇒ 用户看到的话取决于走哪个解析器，排障时对不上账。

**解法入口**：在 `raw.ts` 加一个内部构造器 `unrecognized(raw)`（码 / 文案 / `detail` 形状只在这），四处全部调它。

### TD-01-19 `errOf` 用 `CORRUPT` 报「文件无法识别」

「信封里没有 `err` 字段」是**通道**给错了，不是**文件**坏了。报 `CORRUPT` 会让人去修一个没坏的文件；`MSG.badPayload` 才是这句该说的话。

**解法入口**：`errOf` 的失败分支改用 `unrecognized`（与 TD-01-18 同一处改）。

### TD-01-20 `err:1` 在两个解析器里是两个码

| 解析器 | `err:1` 的码 |
|---|---|
| `lenientVoid` / `strictData` | `VALIDATION` |
| `strictPayload` | `PS_ERROR` |

宿主拒绝执行（「仅支持添加形状图层的渐变色」「请选择文字图层」）是**条件不满足**，不是执行失败 ⇒ 统一 `VALIDATION`。

**解法入口**：加 `hostRejected(value, raw, fallback)`，三处共用。

### TD-01-21 `ztgl_initSystemList` 返回形状未验

`GOVERNANCE` §4.1 字体行标「列表未验」。`parseSystemFontList` 认「哨兵」与「数组」两种，真机到底回哪种没证据。

### TD-01-22 `ys_useFont` 返回形状未验

`strictVoid` 删除后由 `lenientVoid` 兜：若真机返回 `2` 或其它非白名单值，会被判「返回数据无法识别」——**可能是假失败**。

### TD-01-23 `zt_*` 21 个写只验了 3 个

真机有证据的只有 `layer_font_setFontSize`（`undefined`）、`layer_font_setLeading`（`undefined`）、`zt_setFontVision`（`0`）。其余 18 个（`zt_setFontName` / `zt_setFontSize` / `zt_setFontWordSpacing` / `zt_setFontAllCaps` / `zt_setFauxItali` / `zt_setFontAddBold` / `zt_setFontJustified` / `zt_setTextAlignment` / `zt_setHorizontalCenters` / `zt_verticalCenter` / `zt_setUpDownAlign` / `zt_setBackrgoudAlign` / `zt_alignHorizontal` / `cy_distributedByPitch` / `zt_textBranchMerge` / `zt_createButton` / `zt_switchFontDirection` / `zt_setTranslateText`）返回什么没有记录。任何一个返回非白名单值 ⇒ 新判据会把它判成失败。

### TD-01-24 `mm_layer_kindOf` 出现 `unknown`（已解决）

真机日志（2026-10-30 01:33）四次 `PS_WRONG_LAYER: 当前图层是「未知图层」`（`detail: kind:unknown`）。

**根因（2026-10-30 探针自建文档实测）**：`doc.kinds` 输出
`{"undefined":1,"LayerKind.SMARTOBJECT":1,"LayerKind.TEXT":1,"LayerKind.NORMAL":3}` ——
那个 `undefined` 就是**图层组**：组是 `LayerSet`，**没有 `kind` 属性**，`String(layer.kind)` 得 `"undefined"`，
匹配不到任何分支，于是组永远返回 `unknown:undefined`。

**修法**：`mm_layer_kindOf` 先判 `layer.typename === "LayerSet"` 返回 `group`，再看 `kind`。
探针验证：选中组时 `mm_layer_getState()` 返回 `group|probe-group`（修复前是 `unknown:undefined`）。

## 四、探债（真机新发现）

### TD-01-25 三个「对齐」能力的图层前置挂错了

`zt_setHorizontalCenters` / `zt_verticalCenter` / `zt_setUpDownAlign` 真机返回
`{"err":1,"msg":"请选择3个以上图层后使用"}` / `{"err":1,"msg":"请选择2个以上图层后使用"}` ——
它们是**多选**操作，但能力表给它们挂的是 `requireTextLayer`（单层文字前置）。

后果：单层文字图层上会先通过前置、再被宿主拒绝，报 `VALIDATION` + 宿主原话；
真正需要的是执行前就判「选中 ≥3 / ≥2 个」，说清差几个。

**解法入口**：`capabilities.ts` 三行改 `require: requireSelection(3)` / `requireSelection(2)`；
`capability.test.ts` 里「文字属性类全部带 `requireTextLayer`」那条用例要排除这三行。

### TD-01-26 `img_cya4` 是否影响 vendor 上色未验

颜色改走 vendor 的 `ys_useStyleColor` 之后，`sj_interfaceSet.ini` 的 `img_cya4` 不再由我们判（`mm_style_applyColor` 删掉时一起没了）。
`vendor.README` 记过「`img_cya4 === false` 时跳过填充，缺失按开启」，但那是从**色板面板 jsx** 的行为推的，vendor 内部读不读没有证据。

**两个名字别混**（这是本条最容易看错的地方）：

| 名字 | 文件 | 谁读 | 现状 |
|---|---|---|---|
| `img_cya4` | `sj_interfaceSet.ini` | 官方色板面板 jsx（`if (lsObj.img_cya4 === false) return -1`） | src **0 引用**，jsx 只剩 `mm_diag_vendor` 判文件是否存在 |
| `cyAutoFillColor` | `sj_set.json` | **我们自己的**常用页开关 → `common-use-watcher` → `cy_smartFillColor` / `cy_smartFillLineColor` | 活功能，**不动** |

**后果（若 vendor 读它）**：用户关掉那个开关，上色会静默跳过，而我们没有闸门能拦或提示 —— 表现为「点了没反应、也不报错」。
**反过来（若 vendor 不读）**：这个 ini 键与颜色应用彻底无关，`PS_SKIPPED` 那个码永远不会有生产者，可以从 `RAW_FAILURES` 与 `ErrorCode` 里删掉。

**一次测试同时回答两问**：把 `img_cya4` 设为 `false`，跑一次上色，看返回 `skipped` 还是 `1`。
返回 `skipped` → 保留码、补闸门；返回 `1` 且图层没变 → 保留码、但要在文档里写明「vendor 静默跳过」；返回 `1` 且图层变了 → 删码。
